## Часть I. Организующая рамка — Agent OS

Принято ранее (`Space1_Documentation_Rewrite_Plan.md`, реестр решений): архитектура Space1 организуется по образцу AIOS (LLM Agent Operating System) — не как метафора, а как рабочее разделение ответственности на 6 модулей ядра, поверх которых работают конкретные «приложения» (экономический агент и Цифровой Сад, `01_CONCEPT.md` §I.2 — единый пайплайн, разные источники задач, не два разных ядра).

```
┌───────────────────────────────────────────────────────────────────┐
│  APPLICATION LAYER                                                  │
│  Задачи с source=MARKETPLACE  │  Задачи с source=OWNER_DIRECT       │
│  (01_CONCEPT.md §I.3 — приоритет в очереди, не отдельный пайплайн) │
└───────────────────────────────┬─────────────────────────────────────┘
                                ↓
┌───────────────────────────────────────────────────────────────────┐
│  KERNEL LAYER (Agent OS)                                            │
│  ┌──────────────┐ ┌──────────────┐ ┌──────────────┐                │
│  │  Scheduler    │ │Context Manager│ │Memory Manager │                │
│  │  (Часть IV.1) │ │  (Часть IV.2) │ │  (Часть IV.3) │                │
│  └──────────────┘ └──────────────┘ └──────────────┘                │
│  ┌──────────────┐ ┌──────────────┐ ┌──────────────┐                │
│  │Storage Manager│ │ Tool Manager  │ │Access Manager │                │
│  │  (Часть IV.4) │ │  (Часть IV.5) │ │  (Часть IV.6) │                │
│  └──────────────┘ └──────────────┘ └──────────────┘                │
└───────────────────────────────┬─────────────────────────────────────┘
                                ↓
┌───────────────────────────────────────────────────────────────────┐
│  INFRASTRUCTURE LAYER                                                │
│  LLM-провайдеры (ai_super_router) │ MCP-серверы │ Файловое/векторное │
│  хранилище │ Внешние агенты (A2A) │ Платёжные протоколы (AP2)        │
└───────────────────────────────────────────────────────────────────┘
```

**Обоснование, почему не изобретается новое разбиение.** AIOS — не единственная возможная организация, но она уже была выбрана как согласованная рамка ранее, подтверждена независимым исследованием (промышленная и академическая практика), и — что важнее для этого документа — **не противоречит** ни одному уже написанному фрагменту `02`/`03`: каждая функция ядра и каждый этап пайплайна однозначно попадает в один из 6 модулей без остатка (проверено ниже, Часть II) и без насильственной подгонки.

## Часть II. Отображение: 12 этапов пайплайна → 6 модулей ядра

| Этап `03_PIPELINE_MATH.md` | Модуль AIOS | Комментарий |
|---|---|---|
| I. Приём и классификация | Context Manager | Формирует $\mathbf x, H_{TZ}$ — сырьё для контекста |
| II. Сборка контекста (StatusBlock) | Context Manager | Основная зона ответственности модуля |
| III. Оценка (прогноз + цена) | Scheduler | Оценка — подготовка к решению, зона планировщика |
| IV. Compliance-гейт (Γ) | Access Manager | По определению |
| V. Решение 𝒟(T) | Scheduler | Ядро планировщика |
| VI. Декомпозиция | Scheduler | Построение плана — классическая функция планировщика |
| VII. Делегирование/маршрутизация (UCB1) | Scheduler + Tool Manager | Выбор *кого* назначить — пересечение: решение о назначении (Scheduler) использует реестр доступных исполнителей (Tool Manager) |
| VIII. Вызов инструментов | Tool Manager | По определению |
| IX. Оценка качества результата | Scheduler | Используется в следующем решении (§V повторно, для остатка плана) |
| X. Рефлексия и коррекция | Scheduler | Тот же цикл принятия решений, другая точка входа |
| XI. Обновление памяти и метрик | Memory Manager + Storage Manager | Запись — Memory Manager, физическое хранение — Storage Manager |
| XII. Такт пересмотра Mission | Scheduler | Периодический/событийный вызов той же машины решений |

**Вывод из таблицы.** Scheduler — самый нагруженный модуль (7 из 12 этапов), что ожидаемо: это буквально оркестратор, реализующий `02_MATHEMATICAL_CORE.md` и большую часть `03_PIPELINE_MATH.md`. Остальные 5 модулей — по сути специализированные сервисы, которые Scheduler вызывает. Это ценная проверка сама по себе: если бы разбиение получилось равномерным по всем 6 модулям, это было бы подозрительно (означало бы, что решающая логика размазана, а не сосредоточена) — концентрация в Scheduler подтверждает архитектурный принцип `01_CONCEPT.md` §II.1 («оркестратор — мозг»).

## Часть III. Сверка с «формулой идеального планировщика» — закрывает вопрос, оставленный открытым в предыдущей сессии

При разборе «Бесплатные_AI_агенты.docx» была найдена рамка из 8 ролей планировщика: Decomposer, Forecaster, Executor, Verifier, Reflector, Replanner, Synthesizer, Memory. Явная сверка с уже написанным пайплайном:

| Роль | Есть в `03_PIPELINE_MATH.md`? | Где |
|---|---|---|
| Decomposer | ✅ | Этап VI |
| Forecaster | ✅ | Этап III |
| Executor | ✅ | Этапы VII–VIII |
| Reflector | ✅ | Этап X |
| Replanner | ✅ | Этап X (ветка RETRY с заменой действия) |
| Memory | ✅ | Этап XI |
| Synthesizer | ✅ | Этап VIII.5 — явная процедура `synthesize()`, специфичная по типу деливерабла |
| Verifier | ✅ | Этап VIII.6 — трёхуровневая проверка (структурная → автоматическая/тесты → LLM-as-judge) **до** сдачи, отдельно от пост-фактум оценки (Этап IX) |

**Вывод:** пайплайн Space1 покрывает 8 из 8 ролей «идеального планировщика». Verifier и Synthesizer не были предусмотрены в самой первой версии этого документа и добавлены по итогам именно этой сверки — решение получилось более обстоятельным, чем минимальная точечная правка: не бинарный флаг «прошло/не прошло» поверх уже существующего $G_i$, а отдельная трёхуровневая процедура (структура → автоматика/тесты → LLM-as-judge), встроенная в пайплайн как самостоятельный шаг перед сдачей клиенту, а не размазанная по guardrail-проверкам отдельных действий. Это существенно: brak технического характера теперь отсеивается до того, как повлияет на $\Upsilon$, а не после.

## Часть IV. Компоненты и их ответственность

### IV.1 Scheduler

**Ответственность:** этапы III, V, VI, VII (частично), IX, X, XII пайплайна — всё, что решает *что делать дальше*.
**Не отвечает за:** сам вызов LLM/инструментов (это Tool Manager), физическое хранение состояния (Storage Manager).
**Ключевые классы** (по `NAMING_CONVENTION.md`): `Orchestrator` (главный цикл, реализует базовое уравнение `03_PIPELINE_MATH.md` §0.1), `DecisionEngine` (𝒟(T), ядро §IV.14), `MissionPolicy` (ядро §IV.12), `TaskQueue` (приоритизация — `01_CONCEPT.md` §I.3).
**Единственный модуль, которому разрешено вызывать `DecisionEngine`** — ни Context Manager, ни Tool Manager не принимают решений о REJECT/CLARIFY/EXECUTE самостоятельно, только поставляют Scheduler'у данные для решения.

### IV.2 Context Manager

**Ответственность:** этапы I–II пайплайна — классификация задачи и сборка `StatusBlock`.
**Ключевые классы:** `TaskClassifier` (§I.1–I.2 пайплайна), `StatusBlockRenderer` (§II.2 пайплайна, чистая функция форматирования — ядро контракта: НЕ вызывает LLM внутри себя, уже зафиксировано в Приложении A `03_PIPELINE_MATH.md`).
**Явная граница ответственности:** Context Manager формирует то, что *подаётся* в LLM-вызовы, но не решает, *когда* эти вызовы делать — это прерогатива Scheduler и Tool Manager.

### IV.3 Memory Manager

**Ответственность:** этап XI (частично) — интерпретация того, что писать в память и как читать (приоритет $I=w_1\text{Recency}+w_2\text{Importance}+w_3\text{Relevance}$, ядро/пайплайн интерфейс). Полная спецификация — `05_MEMORY_AND_STATE.md`.
**Ключевые классы:** `EpisodicMemoryStore`, `SemanticMemoryStore`, `ProceduralMemoryStore`, `WorkingMemoryBuffer` (4-уровневая CoALA-схема, реестр решений).
**Граница с Storage Manager:** Memory Manager знает *что* и *зачем* хранить (семантика: эпизод, факт, навык), Storage Manager знает *как* — на каком физическом бэкенде (файл, векторная БД, граф).

### IV.4 Storage Manager

**Ответственность:** физический слой хранения — не описан математически ни в `02`, ни в `03` (сознательно — это инфраструктурная, не решающая логика). Обеспечивает персистентность `AgentState`, истории задач, лога для будущей калибровки (ядро §VIII.1 — тройки $(s_t,a_t,r_t)$).
**Ключевые классы:** `StateStore`, `TaskLogStore`, `VectorIndex`, `GraphIndex` (последние два — детали в `05_MEMORY_AND_STATE.md`).

### IV.5 Tool Manager

**Ответственность:** этапы VII (частично) — VIII пайплайна: реестр доступных исполнителей (LLM-провайдеры через `ai_super_router`, MCP-инструменты, внешние суб-агенты), фактический вызов, retry-политика.
**Ключевые классы:** `ExecutorRegistry` (кандидаты для UCB1, §VII.1 пайплайна), `MCPClient` (уже частично реализован в коде — `digital_garden/protocols/mcp_client.py`, сохраняется как основа), `RetryPolicy` (§VIII.2 пайплайна).
**Полная спецификация протоколов (A2A/MCP/AP2) и Tool Acquisition — `09_ECOSYSTEM_AND_INTEROP.md`.**

### IV.6 Access Manager

**Ответственность:** этап IV пайплайна (Γ-гейт) и весь `10_SECURITY.md`. Единственный модуль с правом безусловного запрета — ни один другой модуль не может обойти его решение.
**Ключевые классы:** `GammaVeto` (ядро §IV.1, уже зафиксировано в `NAMING_CONVENTION.md`), `HardRuleRegistry`, `HumanApprovalGate` (`01_CONCEPT.md` §III.2 — конкретные пороги, требующие подписи человека).
**Принципиально:** Access Manager вызывается **до** Scheduler начинает планирование (этап IV предшествует этапу V, VI) — экономика вычислений, уже обоснованная в `03_PIPELINE_MATH.md` §IV.

## Часть V. Суб-агенты — манифест-паттерн

Формализация уже принятого решения (`03_PIPELINE_MATH.md` §VII.1 — функциональное назначение, не ролевое деление; практика Claude Code — декларативный манифест, одноуровневая иерархия):

```yaml
# Пример манифеста суб-агента (не код — контракт формата)
name: "copywriting-executor"
description: "Выполняет атомарные действия категории copywriting"
allowed_tools: ["llm.generate_text", "memory.search_episodic"]
max_context_tokens: 8000
invocation_condition: "action.category == 'copywriting'"
parent_depth: 0  # суб-агенты не могут порождать суб-агентов (одноуровневая иерархия)
```

**Правила, зафиксированные здесь как архитектурные (не как формулы — те уже в `03` §VII.1):**
1. Суб-агент получает только те инструменты, что перечислены в `allowed_tools` — Tool Manager обязан отклонить любой вызов вне этого списка на уровне инфраструктуры, не полагаясь на то, что суб-агент «сам не станет».
2. Суб-агент получает контекст, ограниченный конкретным атомарным действием $a_i$ (§VII.1 пайплайна), а не всю историю задачи — за исключением явного флага `needs_full_history` (используется на этапе рефлексии, §X пайплайна, когда требуется отладка на всей истории попыток).
3. `parent_depth` строго 0 — суб-агенты не вызывают других суб-агентов; если атомарное действие требует дальнейшей декомпозиции, оно возвращается на этап VI (декомпозиция), не порождает вложенный вызов в обход Scheduler.

## Часть VI. Два продукта, один пайплайн — архитектурная реализация решения `01_CONCEPT.md`

Явное подтверждение на уровне архитектуры: не существует отдельного модуля «Цифровой Сад» с собственным Scheduler'ом. Единственное различие в обработке задачи с `source=OWNER_DIRECT` — приоритет в `TaskQueue` (Scheduler, §IV.1) и, если принят вариант (б) из открытого вопроса `01_CONCEPT.md` §I.4, специфичный Mission-профиль при вызове `MissionPolicy.calibrate()`. Ни то, ни другое не требует отдельного экземпляра `Orchestrator`, `DecisionEngine` или любого другого класса Scheduler — один и тот же объект `Orchestrator` обрабатывает оба источника задач.

## Часть VII. Сверка с альтернативной 5-слойной архитектурой (найдена при разборе «Бесплатные_AI_агенты.docx»)

Источник предлагал организовать агента-фрилансера в 5 слоёв (Reactive/Execution/Operational/Tactical/Strategic), каждый — со своим методом планирования (Event-Driven+Online / ReAct+Reflexion / HTN+CPM / HTN+ToT+ILP / RL). Проверка на совместимость с уже принятой AIOS-рамкой (Часть I), а не замена:

| Слой источника | Соответствие в архитектуре Space1 |
|---|---|
| Reactive (Event-Driven) | Триггер обработки очереди (`01_CONCEPT.md` §I.3) + Access Manager (немедленная реакция на hard-нарушения) |
| Execution (ReAct+Reflexion) | Этапы VII–X пайплайна (Tool Manager + Scheduler) |
| Operational (HTN+CPM) | Этап VI пайплайна (декомпозиция) |
| Tactical (HTN+ToT+ILP) | Этап VI при высоком $H_{TZ}$ — там, где нужно оценить несколько альтернативных планов, а не один (см. §III.1 ниже) |
| Strategic (RL) | Ядро §VIII (MDP-рамка для будущего самообучения) + такт Mission (этап XII) |

**Вывод.** Это не другая архитектура, а другой разрез той же системы — источник делит по *временному горизонту решения* (реактивно/тактически/стратегически), AIOS делит по *типу ответственности* (что за модуль). Оба разреза корректны одновременно и не конфликтуют — Space1 использует AIOS как основной (уже написана вся математика под него), но 5-слойное деление полезно как проверочная рамка при написании кода: если какой-то код одновременно относится и к Reactive, и к Strategic слою в этой сверке — это сигнал, что зона ответственности размыта, стоит разделить.

### VII.1 Единственное содержательное дополнение из этой сверки — Tactical-режим декомпозиции

Источник предлагает: для задач с высокой неопределённостью декомпозиции полезно оценивать **несколько** альтернативных планов параллельно (в духе Tree-of-Thought), а не строить один. Это не противоречит формуле `D^*(T)=\arg\max_A[\ldots]$ (ядро/пайплайн §VI) — она уже написана как максимизация по всем возможным $A$, просто на практике перебирается один жадно построенный план. Уточнение: при $H_{TZ}$ выше порога (тот же порог, что уже используется для CLARIFY, ядро §IV.14) — decomposition строит $k\ge 2$ кандидатов плана и выбирает по той же формуле $\arg\max$, не по первому найденному. Не новая формула — уточнение того, как уже существующий $\arg\max$ вычисляется на практике при высокой неопределённости.

## Часть IX. Модель данных — сквозные объекты

Не повторяет типы из Приложений A `02`/`03` (там — сигнатуры функций), а фиксирует **объекты**, которые живут дольше одного вызова функции и передаются между модулями:

```python
@dataclass
class Task:
    id: str
    source: TaskSource  # MARKETPLACE | OWNER_DIRECT — 01_CONCEPT.md §I.2
    raw_text: str
    attachments: list[Attachment]
    price: float | None  # None → определяется на этапе III.2 пайплайна
    deadline: datetime

@dataclass
class AgentState:
    balance: float
    reputation: ReputationVector  # ядро §IV.5
    active_tasks: list[Task]
    homeostasis: float  # H, ядро §IV.7
    context_budget: float  # C_t, ядро §IV.15
    mission_policy: PolicyParams  # ядро §IV.12

@dataclass
class AtomicAction:
    platform: str; function: str; cost: float; method: str
    expected_outcome: str; flags: dict; risk: float
    required_capabilities: CapabilityVector  # x_{a_i}, пайплайн §VI

@dataclass
class ExecutionAttempt:
    action: AtomicAction
    executor: ExecutorProfile
    result: Any | None
    status: Literal["success", "failed", "pending"]
    guardrail_check: bool  # G_i^objective, Часть III.1 этого документа
```

Все остальные объекты (`PolicyParams`, `Decision`, `ReflectionAction` и т.д.) уже типизированы в Приложениях A документов `02` и `03` — не дублируются здесь.
