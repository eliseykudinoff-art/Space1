## 1. ОПИСАНИЕ СИСТЕМЫ

### 1.1 Что такое Manus

**Manus** — это AI-агент для фриланс-платформы, который:

- **Принимает задачи** от клиентов
- **Декомпозирует** их на атомарные действия
- **Выполняет** действия через LLM и инструменты
- **Максимизирует прибыль** при соблюдении ограничений

### 1.2 Центральная идея

Математическая модель Manus основана на простой, но мощной идее:

> **Агент — это оптимизатор, ограниченный набором правил (compliance) и собственной историей (репутация).**

Ключевые функции модели:
- **Φ (Profit)** — максимизация (R - C) / T
- **Γ (Compliance)** — бинарный veto для безопасности
- **Υ (Reputation)** — долгосрочный капитал
- **U (Utility)** — взвешенная сумма всех целей

### 1.3 Почему математика, а не эвристика

| Подход | Преимущества | Недостатки |
|--------|-------------|-----------|
| **Эвристика** | Просто | Не масштабируется, субъективна |
| **Математика** | Масштабируется, объективна | Сложнее понять, требует калибровки |

Математический подход позволяет:
- Автоматически балансировать противоречивые цели
- Адаптировать поведение к контексту
- Объяснять решения агента

## 3. УПРАВЛЕНИЕ АГЕНТОМ ЧЕРЕЗ МАТЕМАТИКУ

### 3.1 Двухуровневая архитектура

**Оркестратор** (стратегический уровень):
$$U = \lambda_\Phi \cdot \Phi + \lambda_\Upsilon \cdot \Upsilon + \lambda_Q \cdot Q + \lambda_\Omega \cdot \Omega - \lambda_\Psi \cdot \Psi - \lambda_\Gamma \cdot \Gamma$$

**Исполнитель** (операционный уровень):
$$\Xi_{task} = \alpha \cdot Q_{result} - \beta \cdot (O_{time} + O_{cost})$$

> Αгент-исполнитель мыслит категориями Ξ, оркестратор — Φ и U.

### 3.2 Mission как калибратор

Mission определяет веса λ через функцию калибровки:

$$\lambda = Mission.calibrate(mission\_type, personality, context)$$

**Типы миссий:**

| Тип | λ_profit | λ_risk | Характер |
|-----|-----------|--------|----------|
| SURVIVAL | 0.8 | 0.9 | Максимальная осторожность |
| GROWTH | 0.3 | 0.5 | Фокус на обучении |
| MAINTENANCE | 0.3 | 0.4 | Стабильность |
| MAXIMIZE | 0.5 | 0.3 | Баланс |
| PREMIUM | 0.2 | 0.3 | Качество важнее прибыли |
| CHARITY | 0.1 | 0.2 | Обучение важнее всего |

### 3.3 Цикл принятия решения

```
TASK INPUT
     │
     ▼
┌─────────────────┐
│ FEATURE EXTRACT  │  e, complexity, d, H
└────────┬─────────┘
         │
         ├──────────────────┐
         ▼                  ▼
┌─────────────────┐  ┌─────────────────┐
│     ROUTER      │  │    QUALITY      │
│   D(T) = ?      │  │   Q(task)      │
└────────┬─────────┘  └────────┬────────┘
         │                  │
         ▼                  ▼
┌─────────────────────────────────────────┐
│            COMPLIANCE CHECK              │
│           Γ(action) = 0 или -∞          │
└────────┬────────────────────────────────┘
         │
         ▼
┌─────────────────────────────────────────┐
│            ATOMIC DECOMPOSE              │
│        D*(T) = argmax [U - λ·C]        │
└─────────────────────────────────────────┘
```

### 3.4 Что определяет поведение агента

| Приоритет | Функция | Влияние |
|----------|--------|--------|
| 1 | **Γ (Compliance)** | Hard constraint — отвергает недопустимые действия |
| 2 | **M (Mission)** | Определяет веса всех λ |
| 3 | **Φ, Υ, Ω** | Utility decomposition |
| 4 | **Q, Ψ** | Soft constraints — штрафуют |
| 5 | **VoI, H** | Когда действовать |

## 4. ЛОГИЧЕСКИЙ АНАЛИЗ

### 4.1 Согласованность модели

**Проверка размерностей (100%):**

| Выражение | Проверка |
|----------|----------|
| P · S · Q | $/задача · 1 · задач/час = $/час ✅ |
| Φ = (R-C)/T | ($/час - $/задача) / час/задача = $/час ✅ |
| H = F_rein/F_bal | ($ + $ + ...)/($ + $ + ...) = 1 ✅ |
| VoI = E[Φ] - E[Φ] | $/час - $/час = $/час ✅ |

### 4.2 Граничные условия

| Переменная | Min | Max | Тип |
|-----------|-----|-----|-----|
| S | 0 | 1 | Hard constraint |
| Q | 0 | 1 | Hard constraint |
| Υ | 0 | 1 | Hard constraint |
| Γ | 0 | -∞ | Veto |
| Φ | -∞ | ∞ | Soft |
| H | ε | 1/ε | Soft (epsilon protection) |

### 4.3 Циклические зависимости

**ЦИКЛ 1: Υ ↔ Φ (Репутация ↔ Прибыль)**
```
Υ ──▶ λ_orders ──▶ Φ ──▶ R ──▶ Υ
```
Осмысленно: хорошая репутация привлекает заказы → больше прибыли → рост репутации.

**ЦИКЛ 2: Γ ↔ Ψ (Compliance ↔ Risk)**
```
Γ ──▶ λ_cost ──▶ Φ ──▶ Ψ ──▶ Γ
```
Осмысленно: строгие правила → более дорогие задачи → выше риск → ужесточение правил.

**ЦИКЛ 3: K ↔ Υ (Knowledge ↔ Reputation)**
```
K ──▶ Υ_ext ──▶ Υ ──▶ learning ──▶ K
```
Осмысленно: знания → лучшие результаты → рост репутации → больше данных для обучения.

## 5. ФИЛОСОФСКИЙ АНАЛИЗ

### 5.1 Миссия изолирована

Согласно архитектуре, **Mission — это отдельный модуль**, который калибрует веса агента, но не является частью оптимизации.

**Это правильно**, потому что:
- Mission определяет "зачем", оптимизация — "как"
- Смешение политики и оптимизации создаёт циклические зависимости
- Агент может менять Mission без переобучения

### 5.2 Γ (Compliance) — бинарный veto

Γ отвергает действия, а не штрафует их. Это **принципиальное отличие**:

| Подход | Интерпретация |
|--------|---------------|
| Γ как штраф | Нарушение правил возможно, но нежелательно |
| Γ как veto | Нарушение правил невозможно |

**Бинарный veto безопаснее**, но требует осторожности при определении правил.

### 5.3 Экономика внимания

Агент имеет ограниченные ресурсы (время, бюджет, контекст). Модель явно учитывает это:

- **VoI** (Value of Information) — сколько стоит уточнение
- **H** (Entropy) — неопределённость как ресурс
- **Complexity ceiling** — предел задач для текущего уровня навыков

### 5.4 Эволюция без катастрофы

Модель предполагает **непрерывную эволюцию**, а не катастрофические переходы:

$$L_s(t) = L_{max} \cdot (1 - e^{-\eta \cdot t^{\gamma}}) + L_0$$

Это означает:
- Новые навыки накапливаются постепенно
- Забывание экспоненциально затухает
- Агент не "перескакивает" через уровни сложности

## 6. ПРОТИВОРЕЧИЯ МОДЕЛИ

### 6.1 Γ threshold — открытый вопрос

**Проблема:** Γ = 0 или Γ = -∞, но что если Γ = -1000?

Это вопрос о **границе принятия решения**. Три варианта:

1. **Жёсткий бинарный:** ACCEPT при Γ = 0, REJECT иначе
2. **Мягкий порог:** ACCEPT при Γ > τ, REJECT иначе
3. **Градуированный штраф:** U_final = U - λ_Γ · (-Γ)

### 6.2 Impulse → Chain — не формализовано

**Проблема:** Механизм трансформации импульса (сенсорный сигнал) в цепочку действий не описан математически.

**Текущая модель:**
```
Impulse → Chain → Prompt → Action
```

**Требуется формализация:**
$$\text{Chain} = f(Impulse, Memory, Context)$$

### 6.3 Внешняя среда — отсутствует

Математическая модель не включает:
- Модель рынка задач
- Модель конкурентов
- Модель клиентов

**Это ограничивает возможности:**
- Предсказания потока заказов
- Ценообразования
- Стратегического планирования

### 6.4 Feedback Loop — обновление метрик

**Проблема:** Нет формулы для обновления состояния:

$$Metrics_{t+1} = f(Metrics_t, Action_t, Environment_t)$$

**Требуется формализация:**
$$\mathbf{S}_{t+1} = \mathbf{S}_t + \alpha \cdot (\mathbf{R}_t - \mathbf{S}_t)$$
