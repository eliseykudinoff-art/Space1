## Часть 0. Каркас документа

### 0.1 Базовое уравнение пайплайна

Весь цикл обработки одной задачи — это одна последовательная трансформация контекста, формально:

$$c_{t+1} = f_\theta(c_t, a_t, o_t)$$

где $c_t$ — состояние контекста на шаге $t$ (агрегат: задача, вектор способностей $\mathbf x$, промежуточные оценки, история попыток), $a_t$ — действие агента на этом шаге (в широком смысле — не только «вызов инструмента», но и «декомпозировать», «уточнить», «оценить качество»), $o_t$ — наблюдение (результат действия). Формула перенесена без изменений из `CYBERNETICS_HOMEOSTASIS_FORMULAS.md» — это не новая идея, а формальная запись уже существовавшего в проекте представления о том, что «агент проходит по этапам», только записанная как явная рекуррентная функция, а не подразумеваемая последовательность шагов.

Базовый цикл исполнения (форма — из того же источника, соответствует общепринятому ReAct-подобному паттерну, использующемуся и в промышленных агентах — см. `Space1_Documentation_Rewrite_Plan.md`, находки по Claude Code/Manus):

```
while not done:
    response = LLM(messages, tools=allowed_tools)
    if has_tool_calls(response):
        results = execute_tools(response.tool_calls)
        messages.append(results)
    else:
        done = True
        return response
```

12 этапов ниже (Часть I–XII) — это не 12 независимых модулей, а 12 последовательных значений $c_t$ на пути одной задачи от приёма до сдачи, каждое со своей формулой перехода к следующему.

## Часть I. Этап 1 — Приём и классификация

**Вход:** сырой текст задачи $T_{raw}$ (текст ТЗ, приложения, контекст переписки с клиентом).
**Выход:** вектор способностей $\mathbf x=(x_1,\ldots,x_{17})$ (вход в `02_MATHEMATICAL_CORE.md`), распределение категорий $p_k$, энтропия $H_{TZ}$ (уже определена в ядре, §IV.9 — здесь определяется, как она вычисляется).

### I.1 Классификация типа и сложности задачи

**Каноническая формула** (перенесена из `Task_Processing/complexity_classification_formula.md`, с обязательным исправлением критического дефекта реализации):

$$\mathbf{e} = \text{Encoder}(T_{raw}) \in \mathbb{R}^d, \qquad \mathbf{p} = \text{softmax}(W_{meta}\cdot\mathbf e + b_{meta}) \in \mathbb{R}^K$$

$$H_{TZ} = -\sum_{k=1}^K p_k\log_2 p_k \qquad \text{(см. } \S\text{IV.9 ядра — формула та же, источник вычисления — здесь)}$$

**Исправленный дефект (критический).** В исходном `complexity_classification_formula.md` матрицы $W_{meta}, b_{meta}$ упоминались в формулах, но нигде не были ни инициализированы, ни обучены — код был неисполним при прямом запуске (переменные не определены). Версия 1.0 этого документа заменяла их «логистической регрессией, обучаемой на накопленном логе задач» — что содержало собственный, не замеченный тогда дефект: на **истинном** холодном старте (первая задача агента, лога ещё нет) обучать регрессию не на чем — та же проблема курицы и яйца, только на шаг глубже. Исправлено при разборе «Бесплатные_AI_агенты.docx», раздел про методы холодного старта:

**Каноническое решение — байесовский переход от популяционного prior к персональному posterior.**
$$\mathbf{p}^{(0)} = \text{prior}(\mathbf{p}\mid\text{industry heuristics}) \quad\xrightarrow{\ n\ \text{задач}\ }\quad \mathbf{p}^{(n)} \propto \mathbf{p}^{(0)} \cdot \prod_{\tau=1}^n \mathcal{L}(\text{outcome}_\tau \mid \text{category}_\tau)$$

где $\text{prior}(\mathbf p)$ — не обучаемые веса, а явные эвристические правила по ключевым словам/структуре текста задачи (доступны с первой секунды работы агента, не требуют данных вообще — например, наличие терминов "API", "интеграция" повышает вероятность категории "разработка"), $\mathcal L$ — правдоподобие по фактическим исходам похожих прошлых задач **этого конкретного агента**, накапливаемое по мере работы (conjugate Beta-обновление по успешности категории, аналогично байесовскому рейтингу $\Upsilon$, ядро §IV.5). $W_{meta}, b_{meta}$ версии 1.0 — не используются как обучаемые параметры вовсе; логистическая регрессия остаётся в реестре Часть XIII как Пост-MVP-опция для этапа, когда данных станет достаточно для честного обучения без переобучения на малой выборке.

**Дополнительный сигнал неопределённости — self-consistency, не только распределение категорий.** Помимо $H_{TZ}$ по $\mathbf p$ (энтропия распределения категорий), вычисляется независимый сигнал через $m$ повторных LLM-оценок сложности задачи с ненулевой температурой:
$$\sigma_{consistency} = \text{std}\left(\{\text{complexity\_estimate}_j\}_{j=1}^m\right)$$
Большой разброс оценок при том же тексте задачи — самостоятельный, дополняющий $H_{TZ}$ признак плохо определённой задачи (например, категория определена уверенно, но внутри категории оценки сложности сильно расходятся — то, что энтропия по категориям не ловит вовсе). Используется как дополнительное условие в решающем правиле $\mathcal D(T)$ (ядро §IV.14) наравне с $H_{TZ}$, не заменяет её.

**[пример]** $T_{raw}$ = «написать промо-текст для лендинга, дедлайн 3 часа, бюджет \$40» → на первой же задаче (без истории) эвристический prior уверенно относит её к категории «копирайтинг» ($p^{(0)}_{copywriting}=0.7$ — характерные ключевые слова), $H_{TZ}=0.88$ бит (умеренная неопределённость, prior менее уверен, чем обученная модель была бы); 5 независимых LLM-оценок сложности дают близкие значения ($\sigma_{consistency}$ низкая) — задача, несмотря на отсутствие истории, признаётся достаточно понятной для EXECUTE, а не автоматического CLARIFY.

### I.2 Извлечение вектора способностей

$$x_i = g_i(T_{raw}, \mathbf p, \text{метаданные клиента}), \quad i=1,\ldots,17$$

Каждая $g_i$ — простое, явное правило (не нейросеть) на MVP-этапе: часть факторов извлекается напрямую из метаданных (например, $x_3$ MCP — есть ли у задачи признаки, требующие внешних интеграций, по ключевым словам и вложениям), часть — из категории $\mathbf p$ (например, копирайтинг не требует $x_{10}$ Browser Automation — фактор получает низкое базовое значение по таблице категория→фактор). Таблица $g_i$ по всем 17 факторам — Часть XIII, запись P-2 (перенесена из `capability.txt`/`capability_2.txt` без изменений: это единственная часть корпуса, где для части факторов есть реальные внешние бенчмарки).

**Обоснование, почему не единая модель на 17 выходов сразу.** Исходный `complexity_classification_formula.md` предполагал единую нейросеть с 17 выходами. **Отклонено для MVP** — 17-мерная регрессия требует значительно больше размеченных данных, чем единичная категоризация из §I.1; вместо этого сложность выносится в явные, проверяемые правила $g_i$, которые проще откалибровать по отдельности и проще отлаживать, когда что-то идёт не так (у нейросети с 17 выходами непонятно, какой из них ошибся и почему).

**Границы:** $H_{TZ}\in[0,\log_2 K]$; $\mathbf x \in [0,1]^{17}$.

**Параметры:** Часть XIII, записи P-1 (отклонённая нейросетевая версия), P-2 (таблица $g_i$).

## Часть II. Этап 2 — Сборка контекста (мост «сигнал → промт»)

**Вход:** $\mathbf x$, $H_{TZ}$ из этапа 1; текущее состояние агента $H$ (гомеостаз, ядро §IV.7), $\Lambda$ (диагностика, §IV.8).
**Выход:** структурированный системный контекст для LLM-вызовов на последующих этапах.

### II.1 Отказ от прежней версии (4 захардкоженных шаблона)

Прежний `SignalBridge` (`PROJECT_NOTE_backup.md`) переводил $H$ в один из 4 текстовых блоков по порогу — раскритиковано в `Space1_Review_and_Roadmap.md` §2.7 как решение более грубое, чем сама задача требовала, и никогда не учитывающее память, несмотря на то что это было явным требованием постановки.

### II.2 Каноническая формула — recitation (Manus-паттерн)

Вместо одноразового перевода состояния в текст — **постоянно переписываемый статус-блок**, дописываемый в конец контекста на каждом шаге пайплайна (не только один раз при приёме задачи):

$$\text{StatusBlock}(t) = \text{render}\Big(H(t),\ \{(v_j, \text{target}_j, \text{deviation}_j)\}_{j\in\text{top-3 отклонений}},\ \text{TrendOf}(H, w{=}5),\ \text{Plan}_{remaining}(t)\Big)$$

где top-3 отклонения — три переменные состояния (`balance_ratio`, `rating_ratio`, `workload_ratio`, `quality_ratio` из §IV.7 ядра) с наибольшим вкладом в текущий `stress`, $\text{TrendOf}(H,w{=}5)$ — направление изменения $H$ за последние 5 шагов (растёт/падает/стабильно), $\text{Plan}_{remaining}(t)$ — оставшиеся шаги декомпозиции (Часть VI) на момент $t$, если декомпозиция уже произошла.

**render()** — не нейросеть и не LLM-вызов, а шаблонизация по структурированным данным (Jinja-подобная, без семантического выбора «какой из 4 абзацев показать») — принципиальное отличие от прежней версии: раньше LLM получал один из 4 заранее написанных текстов, теперь — всегда одну и ту же структуру, заполненную актуальными числами и заголовками отклонений, обновляемую каждый шаг.

**Обоснование выбора именно такого механизма.** Паттерн подтверждён боевой практикой (Manus — см. `Space1_Documentation_Rewrite_Plan.md`, находки этой сессии): переписывание статус-блока в конец контекста на каждом шаге смещает внимание модели обратно к текущему состоянию и плану, компенсируя эффект «потери в середине» длинного контекста — известную и измеренную проблему длинных LLM-диалогов. Это не заменяет решающее правило $\mathcal D(T)$ (§IV.14 ядра, которое остаётся детерминированным кодом, не LLM-выбором) — `StatusBlock` только информирует LLM-вызовы на этапах декомпозиции/исполнения/рефлексии о текущем контексте, само решение REJECT/DECLINE/CLARIFY/EXECUTE принимается до и без участия LLM.

**Связь с памятью — закрывает исходное требование, которое `SignalBridge` игнорировал.** $\text{Plan}_{remaining}$ и top-3 отклонений при формировании обогащаются релевантными эпизодами из памяти (`05_MEMORY_AND_STATE.md`, формула приоритета $I=w_1\text{Recency}+w_2\text{Importance}+w_3\text{Relevance}$) — например, если top-отклонение — `rating_ratio`, в `StatusBlock` добавляется краткая выдержка из последних 1–2 эпизодов, где рейтинг проседал, и что тогда сработало.

**[пример]** Для сквозной задачи: $H=1.05$ (NORMAL), топ-отклонение — `workload_ratio` (агент близко к максимальной загрузке, но не критично) → `StatusBlock` явно указывает LLM на последующих этапах: «текущая загрузка приближается к пределу, при決策 о декомпозиции предпочитать более короткие/простые планы, не начинать параллельные многошаговые задачи».

**Границы/защита:** $\text{StatusBlock}$ ограничен по длине (константа $L_{max}$, Часть XIII) — при превышении применяется сжатие через удаление наименее значимых (по весу $I$) элементов, а не обрезка текста произвольно.

**Отклонённая версия:** Часть XIII, запись S-1 (исходные 4 захардкоженных шаблона `SignalBridge`).

## Часть III. Этап 3 — Оценка (прогноз до исполнения)

**Вход:** $\mathbf x$ (этап 1), $\text{StatusBlock}$ (этап 2).
**Выход:** $\hat\Phi, \hat Q_{predicted}, \hat\Psi$ — прогнозные (не пост-фактум) версии функций ядра; $P$ — предлагаемая цена, если она не задана клиентом (§III.2).

### III.1 Ансамблевый прогноз с холодным стартом (заменяет простое косинусное усреднение — по итогам разбора «Бесплатные_AI_агенты.docx»)

Прежняя версия этого раздела прогнозировала $\hat Q_{comp},\hat Q_{acc},\hat Q_{full}$ единственным способом — байесовским усреднением по похожим прошлым задачам через косинусное сходство векторов $\mathbf x$. Это надёжно работает при богатой истории, но **не работает в первые недели жизни агента**, когда похожих задач ещё нет вовсе — то есть именно тогда, когда прогноз нужнее всего. Заменено на явный ансамбль трёх независимых источников оценки, с весами, сдвигающимися по мере накопления опыта:

$$\hat{v} = w_{ref}(n)\cdot v_{ref} + w_{bayes}(n)\cdot v_{bayes} + w_{llm}(n)\cdot v_{llm}, \qquad n = \text{число завершённых задач агента}$$

где $v\in\{\hat Q_{predicted}, \hat T, \hat\Psi\}$ (одна и та же схема ансамблирования для всех трёх прогнозируемых величин), а источники:

- **$v_{ref}$ — Reference Class Forecasting** (метод Даниэля Канемана — «внешний взгляд»): статистика по задачам **той же категории**, выполненным **не обязательно этим агентом** (population-уровень, не персональный) — базовая ставка успеха/длительности плюс явные поправки за конкретные признаки задачи (та же таблица `risk_premium`, ядро §IV.4 — переиспользуется здесь напрямую, не дублируется вторым набором коэффициентов).
- **$v_{bayes}$ — байесовское усреднение** по собственной истории агента (прежний механизм, сохранён без изменений, но больше не единственный).
- **$v_{llm}$ — LLM self-consistency, калиброванная через Platt Scaling** (уточнение по итогам разбора `FREELANCE-OPT_v3.0_Complete_Architecture.txt`): несколько независимых прогонов классификатора/LLM-оценки над описанием задачи (этап 1) дают «сырую» уверенность $\text{conf}_{raw}$ (согласие между прогонами) — использовать её напрямую как вероятность методологически некорректно: LLM систематически плохо откалиброваны (уверенность 0.9 не означает 90% фактической точности). Калибровка — стандартная логистическая регрессия на исторических парах (сырая уверенность, фактический исход):
$$v_{llm} = \sigma(\alpha_{Platt}\cdot\text{conf}_{raw}+\beta_{Platt}) = \frac{1}{1+e^{-(\alpha_{Platt}\cdot\text{conf}_{raw}+\beta_{Platt})}}$$
обучается через MLE на паре $(\text{conf}_{raw}, \text{outcome})$, накопленной по мере работы агента (та же история задач, что используется для $v_{bayes}$ — не отдельный источник данных). До накопления достаточной истории для обучения $\alpha_{Platt},\beta_{Platt}$ (порог — Часть XIII) — используется identity-калибровка ($\alpha=1,\beta=0$, то есть сырая уверенность как есть) с явной пометкой в логах, что калибровка ещё не обучена. Детализация вызова самой LLM-оценки — `09_ECOSYSTEM_AND_INTEROP.md`, калибровка выхода — здесь.

**Веса по стадии жизни агента** (не откалиброваны на данных Space1, взяты как обоснованная стартовая точка из источника — статус [Б]/[О] смешанный, Часть XIII):

| Число завершённых задач $n$ | $w_{ref}$ | $w_{bayes}$ | $w_{llm}$ |
|---|---|---|---|
| $n<5$ (холодный старт) | 0.4 | 0.2 | 0.4 |
| $5\le n<20$ | 0.2 | 0.5 | 0.3 |
| $n\ge 20$ | 0.1 | 0.7 | 0.2 |

**Обоснование сдвига весов.** На старте у агента физически нет собственной статистики — байесовский прогноз опирается на population prior, слабее reference class и LLM-анализа конкретного текста задачи. По мере накопления опыта персональная байесовская оценка становится точнее общей статистики по категории (агент отличается от «среднего фрилансера» в категории) — вес смещается к ней. Это не эвристика, придуманная для Space1, а прямое применение общего принципа холодного старта: внешний взгляд (reference class) корректирует систематическую переоценку собственной уникальности (inside view bias) именно тогда, когда своих данных ещё нет.

$$\hat\Psi = \hat P_{fail}(\mathbf x)\cdot(C_{direct}+C_{reputation}), \qquad \hat P_{fail} = P_{base}\cdot(1+\text{risk\_premium}(T))$$
— использует таблицу `risk_premium` напрямую (ядро §IV.4), не отдельный набор коэффициентов.

**Границы:** если для категории $\mathbf p$ нет вообще никакой статистики (полный холодный старт и по агенту, и по категории — самый первый случай в истории системы) — $v_{ref}$ падает к общерыночным дефолтам (Часть XIII, запись P-3), не к нулю и не через деление на ноль.

**[пример]** $n=2$ (агент только начал работу) → веса (0.4, 0.2, 0.4). Reference class по категории «копирайтинг» (population-статистика) даёт $\hat Q_{ref}=0.75$; персональная байесовская история почти отсутствует, $\hat Q_{bayes}=0.5$ (population prior); LLM self-consistency по тексту задачи даёт $\hat Q_{llm}=0.82$ (задача несложная) → $\hat Q_{predicted} = 0.4\cdot0.75+0.2\cdot0.5+0.4\cdot0.82 = 0.728$.

### III.2 Определение цены — новая возможность (если цена не задана клиентом)

Прежние версии документации подразумевали, что цена $P$ (ядро, Аксиома A2) — заданный вход. На реальном рынке фриланса цену часто предлагает сам агент (отклик на открытую вакансию, а не фиксированный прайс-лист). Формула — без изменений математической структуры ядра, только определяет, откуда берётся $P$, когда он не дан:

$$P_{bid} = \hat T(\mathbf x)\cdot r_{base}\cdot(1+\text{risk\_premium}(T)+\text{urgency}(H,\text{Mission})+\text{client\_adj}(\Upsilon_{client}))$$

где $r_{base}$ — скользящая (экспоненциально взвешенная) средняя эффективная почасовая ставка агента за последние 20 задач; $\text{urgency}$ — поправка, завязанная на уже существующую Mission-калибровку (§IV.12 ядра: при Mission-профиле, близком к `SURVIVAL`, скидка, при близком к `PREMIUM`/`GROWTH` — надбавка — не новый механизм, а применение уже вычисленных Mission-весов к ценообразованию); $\text{client\_adj}$ — поправка по истории конкретного клиента (повторный клиент — скидка за лояльность, высокая доля правок в прошлом — надбавка).

**Обязательный гейт: минимально допустимая цена.**
$$P_{min} = C_{platform}+C_{processing}+C_{tokens} + \hat T(\mathbf x)\cdot r_{floor}$$
— ниже этой цены задача не должна предлагаться ни при каком Mission-профиле ($r_{floor}$ — абсолютный минимум почасовой ставки, ниже которого экономический смысл предложения отрицательный даже без учёта риска). Это самостоятельный, более строгий гейт, чем общий $\mathcal D(T)$ (§IV.14 ядра) — $P_{bid}$ вычисляется и проверяется на $P_{min}$ **до** решения $\mathcal D(T)$, потому что $\mathcal D(T)$ уже принимает $P$ как известную величину.

**Обоснование, почему это не меняет архитектуру.** Логика ценообразования — чистая функция, добавленная перед этапом 5 (решение), не новый этап пайплайна и не отдельная система: она просто заполняет $P$, когда его не хватало, тем же составом уже существующих величин ($\hat T$, риск-таблица, Mission-веса, $\Upsilon$).

**Границы:** $P_{bid} \ge P_{min}$ всегда, по построению (если $P_{bid}<P_{min}$ по формуле выше — это сигнал, что либо $r_{base}$ занижен, либо задачу в принципе не стоит предлагать, вне зависимости от переговорной тактики).

**Параметры:** $r_{floor}$ — Часть XIII, запись R-4.

## Часть IV. Этап 4 — Compliance-гейт

**Вход:** формальное описание действия (в данном случае — «принять задачу $T$ на условиях $P, deadline$»), $\hat\Psi$ с этапа 3.
**Выход:** $\Gamma_{hard} \in \{0,-\infty\}$, $\Gamma_{soft}\ge 0$ (ядро §IV.1, без изменений формулы — этот этап только фиксирует момент вызова в пайплайне).

**Момент вызова — принципиально важен.** $\Gamma_{hard}$ проверяется **до** трат ресурсов на декомпозицию (Часть VI) — экономия вычислений: если задача заведомо не пройдёт compliance (например, обнаружен признак запрещённой темы), нет смысла тратить LLM-вызовы на построение плана, которым никто не воспользуется. Это явное архитектурное решение, отсутствовавшее в исходных документах в такой формулировке — там Γ упоминался как «первый гейт» абстрактно, но не было зафиксировано, что именно это означает «до декомпозиции», а не просто «до исполнения».

**[пример]** Задача не нарушает ни одного hard-правила, есть один soft-принцип с небольшим весом (например, «предпочитать инклюзивный тон») → $\Gamma_{hard}=0$ (проходит), $\Gamma_{soft}=0.05$ (небольшой, не блокирующий штраф).

## Часть V. Этап 5 — Mission-взвешенное решение

**Вход:** $\hat\Phi,\hat Q_{predicted},\hat\Psi$ (этап 3), $\Gamma_{hard},\Gamma_{soft}$ (этап 4), $H_{TZ}$ (этап 1), $H$ (текущее состояние), $\text{PolicyParams}$ (ядро §IV.12, вычислено заранее на такте Mission, не пересчитывается для каждой задачи).
**Выход:** решение $\mathcal D(T) \in \{\text{REJECT, DECLINE, CLARIFY, EXECUTE}\}$ — формула из ядра §IV.14 (обновлена: REJECT — жёсткий запрет по Γ, DECLINE — экономический/риск-мотивированный отказ, не запрет), применяется здесь без изменений, этот этап фиксирует, что именно из пайплайна подставляется в каждую переменную формулы:

| Переменная в $\mathcal D(T)$ | Откуда берётся в пайплайне |
|---|---|
| $\Gamma_{hard}(T)$ | Этап 4 |
| $\Psi(T)$ | $\hat\Psi$, этап 3 |
| $C_t$ | Текущее состояние контекстного окна на момент оценки (не за всю историю агента — за текущую сессию работы над задачей) |
| $H_{TZ}$ | Этап 1 |
| $VoI(\text{уточнение})$ | Вычисляется здесь: $\mathbb E[\hat\Phi\mid\text{после уточнения}] - \hat\Phi$ (после уточнения — на исторических данных, где клиент уточнял аналогичные задачи) |
| $H$ | Текущее состояние агента (не связано напрямую с этой задачей) |
| $U(T)$ | Вычисляется из $\hat\Phi,\hat Q_{predicted}$ и текущих $\Upsilon_{scalar},\Omega$ по формуле §IV.11 ядра, с $\Gamma_{soft}$ этапа 4 |

**[пример]** Все гейты пройдены, $H_{TZ}$ низкий, $VoI$ уточнения ниже стоимости паузы → CLARIFY не требуется; $U(T) = 0.34 > 0$, $\hat Q_{predicted}=0.81 \ge q_{min}=0.7$ → **EXECUTE**.

## Часть VI. Этап 6 — Декомпозиция

**Вход:** $T$ (задача, решение EXECUTE), $\mathbf x$.
**Выход:** план $A = (a_1,\ldots,a_n)$ — последовательность атомарных действий.

### VI.1 Перенос семейства формул из ядра без изменений по существу

Весь аппарат $D^*(T)$ из `MATHEMATICAL_FORMULAS.md` §9 (архивирован из ядра как относящийся к пайплайну, `02_MATHEMATICAL_CORE.md` Часть VI) размещается здесь целиком:

$$a = (p, f, c, m, o, \varphi, r) \quad\text{— атомарное действие: платформа, функция, стоимость, метод, ожидаемый результат, флаги, риск}$$

$$u(a) = \text{полезность одного атомарного действия (см. исходную формулу §9.2 архива)}$$

$$D^*(T) = \arg\max_{A} \left[\mathcal U(A,\theta) - \mathcal C(A,\theta)\right]\cdot\mathbb I_{pass}(\Gamma(A)), \qquad \mathcal U(A,\theta)=\sum_i u(a_i) + \sum_{i<j}\rho(a_i,a_j)$$

где $\rho(a_i,a_j)$ — синергия между действиями (например, «прочитать документацию» и «написать код по документации» синергичны сильнее, чем несвязанные действия).

**Формальная связь с $\mathbf x$ (закрывает пробел, отмеченный в интерфейсе ядра, §VII ядра, п.3, и в независимом ревью — декомпозиция и факторы способностей исторически считались разными, не связанными системами).** Каждое атомарное действие $a_i$ порождает частичный вектор требуемых способностей $\mathbf x_{a_i}$ (например, действие с $f=$«вызов внешнего API» требует высокого $x_3$ MCP); задача разбивается только на действия, для которых $\mathbf x_{a_i} \preceq \mathbf x$ (агент обладает достаточной способностью) — иначе действие либо заменяется на альтернативу с более низкими требованиями, либо инициирует Tool Acquisition (`09_ECOSYSTEM_AND_INTEROP.md`), если подходящего инструмента нет вовсе.

**Дельта-фильтрация плана (новая, из `CYBERNETICS_HOMEOSTASIS_FORMULAS.md`, «Внешние кибернетические фильтры»).** После построения плана — проверка, не превышает ли он допустимое отклонение от «типового» плана для этой категории задачи:
$$\Delta_{plan} = \frac{|n - \bar n_{\mathbf p}|}{\bar n_{\mathbf p}}$$
где $\bar n_{\mathbf p}$ — среднее число шагов для задач той же категории. При $\Delta_{plan}$ выше порога (Часть XIII) — план не отклоняется автоматически, но помечается для дополнительного контроля на этапе рефлексии (Часть X) — необычно длинный/короткий план чаще ошибочен.

**Границы:** $n\ge 1$ (минимум одно атомарное действие — тривиальные задачи не декомпозируются дальше одного шага).

**Отклонённая версия:** не отклонена — семейство формул принято целиком, без альтернатив в этом слое (альтернативные декомпозиции не были найдены в корпусе за пределами этого семейства).

### VI.1a Уверенность модулирует не только решение, но и консервативность плана (по итогам полного дочитывания «Оптимизатора фриланс-агента»)

Калиброванная уверенность $v_{llm}$ (Platt Scaling, §III.1) уже используется как вход в ансамблевый прогноз и, агрегированно, в гейт $\mathcal D(T)$ (ядро §IV.14). Дополнение: та же уверенность обязана влиять на **форму** плана $A$, который строит $D^*(T)$, не только на факт «строить ли план вообще»:

$$\text{plan\_mode}(\hat Q_{predicted}) = \begin{cases}
\text{агрессивный}, & \hat Q_{predicted} \ge 0.85 \\
\text{консервативный (+ verification steps, fallback)}, & 0.4 \le \hat Q_{predicted} < 0.85 \\
\text{DECLINE (уже покрыто §V, сюда план не доходит)}, & \hat Q_{predicted} < 0.4
\end{cases}$$

**Практическое отличие «консервативного» режима:** $D^*(T)$ в этом режиме предпочитает планы с дополнительными checkpoint-действиями (промежуточная валидация после ключевых шагов, а не только финальная — тот же Verifier, §VIII.6, но вызываемый раньше и чаще) и с явными fallback-ветками (альтернативное действие, если основное не проходит checkpoint), даже если это увеличивает $\mathcal C(A,\theta)$ — компромисс сознательно смещается в сторону надёжности при среднем доверии к успеху. Технически это не новая формула, а модификатор весов синергии $\rho(a_i,a_j)$ в §VI.1: checkpoint-действия получают положительный бонус к синергии с основными шагами плана только в консервативном режиме.

**Обоснование, почему это не дублирует уже существующий гейт $q_{min}$.** $q_{min}$ (ядро §IV.12) — порог, ниже которого выполнять вообще не стоит (проверяется в $\mathcal D(T)$, до декомпозиции). Этот механизм — про **то, как** выполнять уже одобренную задачу: даже прошедшая гейт задача с $\hat Q_{predicted}=0.5$ должна исполняться иначе, чем задача с $\hat Q_{predicted}=0.95$, при том что обе получили EXECUTE.

### VI.1b Multi-Agent Debate — Пост-MVP опция для решений с высокой ценой ошибки

Для решений декомпозиции с одновременно высоким $H_{TZ}$ (задача плохо определена) и высоким $\Psi$ (ошибка дорого стоит) — единственный LLM-вызов для построения плана может быть недостаточно надёжен. Пост-MVP расширение: вместо одного вызова — структурированные дебаты нескольких функциональных ролей (не персистентных суб-агентов, см. `04_ARCHITECTURE.md` Часть V — роли существуют только на время одного решения и распускаются сразу после), каждая аргументирует свой вариант плана, модератор (отдельный LLM-вызов) оценивает logical validity/relevance/risk-adjusted utility каждого аргумента и выносит решение. Само обсуждение сохраняется в Episodic Memory (`05_MEMORY_AND_STATE.md` §III) как обоснование решения — полезно и для будущего объяснения клиенту, и как материал для калибровки. **Явное согласование с уже принятым принципом функционального (не ролевого) разделения суб-агентов** (`03` §VII.1, источник — практика Manus): роли дебатов не образуют постоянную организационную структуру, они существуют исключительно для одного акта улучшения качества решения — это не противоречие принципу, а его частный случай (роль = функция момента, не должность).

**Статус:** не входит в MVP (увеличивает стоимость декомпозиции в разы, обосновано только для меньшинства задач с высокой ставкой) — условие активации: $H_{TZ} > H_{TZ,max}$ **и** $\hat\Psi$ в верхнем квартиле среди задач той же категории.

### VI.2 Структурные метрики плана и обнаружение конфликтов ресурсов (новое, из разбора «Бесплатные_AI_агенты.docx»)

**Проверяются сразу после построения плана, до перехода к маршрутизации (Часть VII):**

$$\text{Cohesion} = \frac{|E_{internal}|}{|E_{total}|}, \qquad \text{Coupling} = \frac{|E_{external}|}{|E_{total}|}, \qquad \text{Balance} = \frac{1}{1+\text{std}(\{u(a_i)\}_{i=1}^n)}$$

**Обнаружение конфликтов ресурсов («ложный параллелизм»).** Прежде чем два действия $a_i, a_j$ считаются независимыми (могут исполняться параллельно на этапе VII), проверяется пересечение по используемым ресурсам:
$$\text{conflict}(a_i,a_j) = \left(\text{resources}(a_i)\cap\text{resources}(a_j)\ne\emptyset\right)\ \land\ \left(\text{is\_write}(a_i)\lor\text{is\_write}(a_j)\right)$$
При обнаружении конфликта — между $a_i,a_j$ добавляется явная зависимость (упорядочивание по приоритету), план из $D^*(T)$ пересобирается с учётом этого ограничения.

**Обоснование, почему это отдельная проверка, а не часть $D^*(T)$.** $D^*(T)$ (§VI.1) максимизирует полезность декомпозиции, не заботясь о том, физически совместимы ли параллельные ветки (например, два действия, независимо изменяющие один и тот же файл). Без этой проверки агент мог бы запланировать формально «оптимальный», но физически неисполнимый без гонки состояний план — распространённая, задокументированная проблема при параллельном исполнении декомпозированных задач.

### VI.3 Критический путь и слэк (CPM) — связывает декомпозицию с решением об аутсорсе (Часть VII)

$$\text{ES}(a_i) = \max_{a_j \to a_i} \left(\text{ES}(a_j)+\text{dur}(a_j)\right), \qquad \text{slack}(a_i) = \text{LS}(a_i) - \text{ES}(a_i)$$

где $\text{ES}$ — раннее начало, $\text{LS}$ — позднее допустимое начало без срыва дедлайна всей задачи (стандартный Critical Path Method, без модификаций по существу). Действия с $\text{slack}(a_i)=0$ образуют критический путь — любая задержка на них напрямую задерживает сдачу; действия с $\text{slack}(a_i)>0$ имеют запас.

**Связь с Часть VII (используется там как явный вход для решения о делегировании внешним исполнителям).**

**Границы:** $\text{Cohesion},\text{Coupling}\in[0,1]$; $\text{slack}(a_i)\ge 0$ для выполнимого плана (отрицательный слэк означает, что план физически не укладывается в дедлайн — сигнал вернуться на $\mathcal D(T)$, пересмотреть решение или дедлайн).

**Параметры:** нет новых калибруемых констант — CPM детерминирован при известных длительностях $\text{dur}(a_i)$ (оценки времени берутся из уже существующего $T(\mathbf x_{a_i})$, ядро §IV.2).

## Часть VII. Этап 7 — Делегирование и маршрутизация (внутренним и внешним исполнителям)

**Вход:** план $A=(a_1,\ldots,a_n)$.
**Выход:** для каждого $a_i$ — назначенный исполнитель $e_i$ (конкретная LLM-модель через `ai_super_router`, MCP-инструмент, или внешний суб-агент).

### VII.1 Каноническая формула — UCB1 (закрывает исследовательский вопрос «LLM-роутинг как contextual bandit», стоявший в очереди Фазы 1 плана)

$$e_i^* = \arg\max_{e\in\text{Candidates}(a_i)} \left[\bar V_e + c\sqrt{\frac{\ln N}{n_e}}\right]$$

где $\bar V_e$ — средняя historical полезность исполнителя $e$ на действиях этого типа (вычисляется через $\Xi_{task}$, ядро §архив Φ-3/Часть VI, запись про $\Xi_{task}$: $\Xi = \alpha Q_{result} - \beta(O_{time}+O_{cost})$), $N$ — общее число назначений на действия этого типа, $n_e$ — сколько раз конкретно $e$ был выбран, $c$ — константа исследования (выше — больше готовность пробовать малоиспробованных исполнителей).

**Обоснование выбора.** UCB1 — простой, проверенный алгоритм баланса «исследование/использование»: не зацикливается на исторически лучшем исполнителе бесконечно (оставляет шанс новым/малоиспробованным провайдерам, важно, учитывая что `ai_super_router` рассчитан на десятки взаимозаменяемых бесплатных LLM-провайдеров с нестабильной доступностью), и не выбирает случайно (взвешивает по накопленной статистике). Заменяет исходную эвристику «сортировка по цене и приоритету», которая не адаптировалась по фактическому качеству результатов.

**Candidates(a_i) — фильтр перед UCB1.** Из полного списка исполнителей в кандидаты попадают только те, у кого $\text{Trust}(e) \ge \text{trust}_{min}$ (ядро §IV.13) и заявленные возможности покрывают требования $\mathbf x_{a_i}$ (декларация Agent Card/MCP-манифеста, `09_ECOSYSTEM_AND_INTEROP.md`) — UCB1 работает только внутри уже прошедшего порог доверия множества, не заменяет гейт доверия.

**Функциональное, а не ролевое разбиение исполнителей.** По итогам исследования практики Manus (`Space1_Documentation_Rewrite_Plan.md`, реестр решений — открытый пункт о пересмотре ролевого деления `FREELANCER_AGENT_ARCHITECTURE.md`) — каждый $e_i$ назначается **на конкретное атомарное действие $a_i$** и получает только контекст, необходимый для этого действия (не всю историю задачи целиком), кроме случаев, явно требующих полной истории (например, отладка ошибки предыдущего шага, Часть X) — закрывает открытый архитектурный пункт, зафиксированный ранее как «требует решения в Фазе 4»: решение принято здесь, на уровне математики маршрутизации, и будет унаследовано `04_ARCHITECTURE.md`.

**Границы:** если $\text{Candidates}(a_i)=\emptyset$ (ни один исполнитель не проходит порог доверия и не покрывает требования) — действие не назначается, вся задача возвращается на этап 6 с пометкой «недостижимо текущими средствами», что может откатить решение $\mathcal D(T)$ к CLARIFY уже постфактум (редкий, но обрабатываемый случай — не был предусмотрен ни в одной исходной версии).

**Параметры:** $c$ (константа исследования) — Часть XIII, запись R-1.

### VII.2 Решение о делегировании внешним исполнителям — по слэку, не по умолчанию для всех

$$\text{outsource\_eligible}(a_i) = \left(\text{slack}(a_i) > \text{slack}_{min}\right) \ \land\ \left(\exists e \in \text{Candidates}(a_i):\ \text{Trust}(e)\ge\text{trust}_{min}^{outsource}\right)$$

Действия на критическом пути ($\text{slack}=0$) **никогда** не делегируются внешним (менее контролируемым) исполнителям — только внутренним, с наивысшим по UCB1 $\bar V_e$; задержка на критическом пути напрямую задерживает сдачу всей задачи, а внешний исполнитель — источник дополнительной, менее предсказуемой задержки. Действия с достаточным слэком — кандидаты на делегирование более дешёвым (но, возможно, менее быстрым/надёжным) внешним исполнителям, что позволяет снизить $C(\mathbf x)$ без риска для дедлайна.

**Обоснование.** Прямое применение находки из разбора «Бесплатные_AI_агенты.docx»: критический путь — единственная часть плана, которую нельзя доверить менее контролируемому исполнителю, слэк — единственное место, где экономия на аутсорсе не создаёт риска для срока. Без этого правила UCB1 (§VII.1) мог бы выбрать дешёвого внешнего исполнителя и для действия на критическом пути — формально допустимо по чистой полезности $\bar V_e$, но недопустимо с точки зрения общего срока задачи.

### VII.3 Динамическое ценообразование — только для задач, где $P$ не задан площадкой (агент сам формирует предложение)

$$P_{bid} = h_{base}\cdot T(\mathbf x)\cdot(1+\rho_{risk}^{-1}\cdot(1-\rho_{risk}) + \pi_{mission} + \pi_{client})$$

где $h_{base}$ — базовая ставка (экспоненциально взвешенное скользящее среднее по эффективной часовой ставке последних задач, аналогично $K_t$-сглаживанию ядра §IV.2), $\pi_{mission}$ — надбавка/скидка, производная от текущего Mission-профиля (ядро §IV.12: отрицательная при `SURVIVAL`, положительная при `PREMIUM`/`GROWTH` со стабильным $H$), $\pi_{client}$ — корректировка по истории конкретного клиента (скидка постоянному надёжному клиенту, надбавка за высокую историческую частоту правок).

**Обоснование, почему это отдельный, новый подшаг.** До этого разбора $P$ в формулах ядра и пайплайна трактовался как заданная извне величина (цена из листинга биржи или согласованная клиентом) — для случаев, где агент сам формирует предложение цены (типично для открытых заявок на бирже), формулы не давали механизма, как именно $P$ определяется. Формула использует уже существующие величины ($\rho_{risk}$ §IV.2 ядра, Mission-профиль §IV.12 ядра) — не вводит независимый от остального ядра механизм ценообразования.

**Нижняя граница.** $P_{bid}$ не может быть предложен ниже, чем даёт минимальный эффективный часовой порог (ядро §IV.2, $r_{min}$) — связка с уже существующим гейтом, не отдельное правило.

**Границы:** $P_{bid} > 0$. **Параметры:** — Часть XIII, запись R-4.

## Часть VIII. Этап 8 — Исполнение: вызов инструментов, синтез, верификация

**Вход:** $a_i$, назначенный $e_i$.
**Выход:** результат $o_i$ или ошибка; финальный статус после исчерпания повторных попыток; на выходе всего этапа (после §VIII.4–VIII.5) — единый верифицированный черновик деливерabl, готовый к оценке качества (Часть IX).

> **Почему этап переименован и расширен.** Разбор «Бесплатные_AI_агенты.docx» даёт формулу «идеального планировщика» из 8 компонентов (Decomposer/Forecaster/Executor/Verifier/Reflector/Replanner/Synthesizer/Memory), выведенную из сравнения реальных промышленных агентов (Manus, Kimi Swarm, Codex, Google Antigravity) — ни один из них не реализует все 8, но авторы явно показывают, какие компоненты систематически отличают «серьёзного» агента от «игрушечного». Сверка с этим списком показала, что в версии 1.0 этого документа было 6 из 8 компонентов (Decomposer=Часть VI, Forecaster=Часть III, Executor=§VIII.1–3, Reflector/Replanner=Часть X, Memory=Часть XI) — **Synthesizer и Verifier отсутствовали как отдельные шаги полностью**. Это не декоративный пробел: без явного Synthesizer результаты нескольких атомарных действий нигде не сводились в один согласованный деливерabl явной процедурой; без явного Verifier первая проверка качества (Часть IX) происходила уже post-factum, после отправки клиенту — то есть агент мог обнаружить брак только тогда, когда его уже поздно исправлять без ущерба для $\Upsilon$.

### VIII.1 Каскадная вероятность отказа (перенесена из архива ядра, Часть VI ядра, запись Ψ-2 — там отмечена как относящаяся к этому уровню, не к уровню задачи)

$$P_{cascade} = 1 - \prod_{i=1}^{n}(1-p_i), \qquad P_{risk\_final} = P_{fail}\prod_i (1-p_{risk,i}(1-G_i))$$

где $p_i$ — вероятность отказа конкретного шага $a_i$, $G_i\in[0,1]$ — эффективность guardrail-проверки перед этим шагом (фактор $x_{12}$ ядра — Guardrails).

### VIII.2 Политика повторных попыток

$$\text{delay}(k) = \min(\text{delay}_{max},\ \text{delay}_0\cdot 2^k), \qquad k_{max} = \text{round}\left(k_{max,0}\cdot(1-\hat\Psi/\psi_{max})\right)$$

— экспоненциальный backoff (без изменений по существу — общепринятая практика, не была ни разу формализована ни в одном исходном документе Space1, только упоминалась текстом как «нужна обработка ошибок»), но с новой связкой: **допустимое число попыток само зависит от риска задачи** — чем ближе $\hat\Psi$ к порогу $\psi_{max}$, тем меньше попыток агент даёт себе на этот конкретный шаг, прежде чем эскалировать (Часть X), а не тратит их бесконечно на заведомо рискованную задачу.

### VIII.3 Оставлять ошибки в контексте, не скрывать (Manus-паттерн, прямое применение)

После неудачной попытки $o_i^{fail}$ **не удаляется** из контекста последующих попыток — добавляется в $\text{StatusBlock}$ (этап 2, обновляется) как есть, вместе с кратким диагнозом причины (не просто «ошибка», а «превышен таймаут» / «результат не прошёл guardrail $G_i$» / и т.д.). Обоснование — там же (§II.2 этого документа, Manus context engineering) — модель, видящая свою предыдущую ошибку явно, с большей вероятностью не повторяет её на следующей попытке, чем модель, которой просто говорят «попробуй снова» без контекста, что именно пошло не так.

**Границы:** при исчерпании $k_{max}$ попыток без успеха — действие помечается failed, задача уходит на этап 10 (рефлексия) для решения — заменить шаг альтернативным действием, эскалировать клиенту/человеку, или отказаться от всей задачи (пересчёт $\mathcal D(T)$ пост-фактум).

**Параметры:** $\text{delay}_0, \text{delay}_{max}, k_{max,0}$ — Часть XIII, запись R-2.

### VIII.4 Обработка прерываний во время исполнения

$$\text{check\_interrupt}(t) = \exists\ \text{событие} \in \{\text{новое сообщение клиента},\ \text{source=OWNER\_DIRECT задача выше по приоритету (}01\_CONCEPT.md\ \S I.3\text{)},\ \Gamma_{hard}\text{-триггер извне}\}$$

Проверяется между шагами исполнения (не внутри одного атомарного действия — прерывание не обрывает уже начатый вызов инструмента). При срабатывании — текущий прогресс сохраняется как есть (не откатывается), управление передаётся обработчику события; после обработки — исполнение плана продолжается с прерванного места, если событие не изменило сам план (в этом случае — возврат на Часть VI, декомпозиция, с уже готовыми частичными результатами как входом).

**Обоснование.** Обобщение механизма, уже введённого точечно для приоритета задач владельца (`01_CONCEPT.md` §I.3, условие `urgent(current)`) — там речь шла о выборе следующей задачи из очереди, здесь та же логика прерывания распространена на **уже исполняющуюся** задачу, а не только на выбор следующей. Без этого агент, начавший длинный план, не заметит, например, что клиент по ходу дела отменил задачу или прислал критическое уточнение, и продолжит работать вслепую до конца плана.

### VIII.5 Synthesizer — сведение результатов атомарных действий в деливерabl

$$D = \text{synthesize}(o_1,\ldots,o_n,\ A,\ T_{raw})$$

Не отдельная ML-модель, а явная процедура, специфичная для типа задачи (категория $\mathbf p$, этап 1): для программного кода — сборка файлов в проект согласно структуре, заданной в плане $A$; для текстовых деливераблов — объединение секций в порядке, заданном декомпозицией, с проверкой согласованности терминологии между секциями (написанными, возможно, разными исполнителями $e_i$, §VII); для смешанных — упаковка в единый пакет с сопроводительным описанием.

**Обоснование, почему это отдельный шаг, а не часть Часть VI (декомпозиции).** Декомпозиция (Часть VI) определяет, **как разбить** задачу на действия, и неявно — как их результаты **должны** собраться вместе (граф зависимостей). Synthesizer — это шаг, где это сведение **фактически происходит**, после того как реальные (не запланированные) результаты $o_i$ получены — процедура должна уметь обработать случай, когда фактический результат отличается от того, что предполагалось на этапе планирования (например, один суб-агент выбрал другой формат данных, чем ожидалось) — до этого добавления такой случай не был предусмотрен нигде в пайплайне явно.

### VIII.6 Verifier — Worker-Critic Loop (обновлено по итогам разбора RLI-документов)

$$\text{verify}(D) \to \{\text{ACCEPT},\ \text{REVISE}(\text{issues}),\ \text{REJECT}\}$$

**Обоснование обновления.** Прежняя версия (3 уровня: структурная/автоматическая/LLM-as-judge) была логически корректной, но недостаточно конкретной — не задавала ни порогов принятия решения, ни того, что именно проверяется. Разбор Remote Labor Index (RLI — реальный, проверенный бенчмарк на 240 задачах с Upwork, см. `07_CALIBRATION_AND_VALIDATION.md`) даёт эмпирическую структуру провалов, которая должна определять, на чём именно фокусируется Verifier: **45.6%** отказов — плохое качество, **35.7%** — неполные результаты, **17.6%** — технические проблемы, **14.8%** — несогласованность между файлами одной задачи. Три прежних уровня покрывали в основном последние два пункта (17.6%+частично 14.8%) и почти не покрывали первые два (81.3% реальных причин провала). Обновлённая версия — прямой ответ на это распределение, не абстрактное усиление ради усиления.

**Композиция — пять типов критика, не три уровня** (каждый нацелен на конкретную долю провалов выше):

| Критик | Проверяет | Соответствует доле провалов | Модель |
|---|---|---|---|
| **Technical** | Целостность файлов, формат, полнота (все deliverables из брифа присутствуют) | Технические проблемы (17.6%) + часть неполноты (35.7%) | Правило-based + LLM |
| **Brief Compliance** | Явное извлечение требований из $T_{raw}$ и сверка каждого пункта с результатом | Неполные результаты (35.7%) | LLM + структурированное извлечение |
| **Visual/Domain QA** | Эстетика, стиль, соответствие профессиональному уровню — там, где применимо (не для всех категорий) | Плохое качество (45.6%) | Vision-модель для визуальных deliverables, LLM для текстовых |
| **Cross-Deliverable Consistency** | Согласованность между несколькими файлами одной задачи (например, если синтез, §VIII.5, собирал результат из нескольких $o_i$) | Несогласованность (14.8%) | LLM + сравнение |
| **Client Simulation** | Финальный гейт: «заплатил бы клиент за это?», без разбора по критериям — целостная оценка глазами требовательного заказчика | Интегральная проверка поверх всех предыдущих | LLM, роль явно задана как «требовательный клиент», не как ассистент |

**Формула цикла (Worker-Critic, с явными порогами):**

$$\text{score}_k = \text{Critic}_k(D, T_{raw}) \in [0,10], \qquad \text{verdict} = \begin{cases}
\textbf{ACCEPT}, & \min_k \text{score}_k \ge 8.5 \\
\textbf{REVISE}, & \min_k \text{score}_k \in [3, 8.5) \ \land\ \text{iteration} < 4 \\
\textbf{REJECT/ESCALATE}, & \min_k \text{score}_k < 3 \ \land\ \text{iteration}\ge 2
\end{cases}$$

— решение по **минимуму**, не среднему по критикам: сильный результат по эстетике не компенсирует отсутствие обязательного файла (Technical/Brief Compliance). Максимум 4 итерации REVISE (совпадает с уже принятым $k_{max}$ политики повторных попыток, §VIII.2 — не новый, отдельный лимит).

**Почему именно эти цифры (8.5 / 3 / 4 итерации), а не абстрактные [О]-параметры.** Взяты из практики Worker-Critic реализаций, зафиксировавших эмпирически рабочий диапазон для похожей задачи (оценка по рубрике 0–10, порог принятия 8.5, порог безнадёжности 3, потолок итераций 2–4 до infinite-loop риска) — статус параметров ниже помечен [Б]/[О] смешанно (Часть XIII): диапазон обоснован внешней практикой, но не откалиброван на данных именно Space1.

**Важная методологическая оговорка — риск инфляции самооценки.** Авторы RLI, при попытке заменить дорогую ручную оценку автоматическим LLM-судьёй, обнаружили систематическое завышение оценки более новых/сильных моделей — примерно в 2.5–3 раза относительно человеческой оценки на той же выборке. Прямое следствие для Verifier: `Critic` (LLM-as-judge роль) **не может использовать ту же модель**, что и `Worker` (исполнитель, §VII), без калибровки — либо разные модели (cross-model QA: генератор одна модель, критик — другая), либо периодическая сверка меньшей выборки автоматических вердиктов с человеческой оценкой (эта сверка — часть `07_CALIBRATION_AND_VALIDATION.md`, не решается здесь раз и навсегда).

**Связь с остальным пайплайном.** `REVISE` возвращает управление на Executor (§VII–VIII) с конкретными issues от критиков как вход для следующей попытки — механизм тот же, что уже описан в §VIII.3 (ошибки остаются в контексте, не скрываются). `REJECT/ESCALATE` — та же ветка, что уже определена в Часть X (рефлексия), не новый механизм. `ACCEPT` пропускает результат на Часть IX (пост-фактум оценка $Q_{actual}$, где теперь измеряется уже отфильтрованный, а не сырой результат).

**Границы:** Verifier не гарантирует $Q_{actual}=1$ — снижает частоту брака, доходящего до клиента, не заменяет измерение реального восприятия.

**Параметры:** пороги 8.5/3/4 — Часть XIII, запись V-1 (обоснованы внешней практикой, не Space1-данными).

**Отклонённые версии:** прежняя 3-уровневая версия (структурная/автоматическая/LLM-as-judge единым порогом) — не ошибочна, но заменена более детализированной и эмпирически заземлённой; сохранена как более простой вариант для категорий задач, где 5 критиков избыточны (например, тривиальные короткие тексты) — выбор между полной и упрощённой версией Verifier — по категории задачи $\mathbf p$ (этап 1), не универсальное правило.

## Часть IX. Этап 9 — Оценка качества результата

**Вход:** финальный результат задачи (агрегат $o_1,\ldots,o_n$), сданный клиенту.
**Выход:** $Q$ (пост-фактум, ядро §IV.3, без изменений формулы).

Единственное дополнение к формуле ядра — момент и источник измерения $Q_{acc}$: сравнение с намерением клиента происходит через явный, зафиксированный на этапе приёма (§I.1) вектор $\mathbf p$ (распределение категорий) и текст исходного $T_{raw}$ — не через отдельный субъективный LLM-вызов «оцени качество», а через ту же cosine-similarity механику, что уже используется в прогнозе (§III.1), примененную теперь к фактическому результату, а не к историческим аналогам. Это гарантирует, что прогнозная и пост-фактум оценки методологически сопоставимы (проверка $\hat Q_{predicted}$ vs $Q_{actual}$ имеет смысл только если считаются одним способом).

## Часть X. Этап 10 — Рефлексия и коррекция неверных ходов

**Вход:** история попыток (включая неудачные, этап 8), $Q$ (этап 9, если задача дошла до сдачи), любые failed-действия.
**Выход:** одно из: RETRY (с изменённым планом), ESCALATE (человеку/клиенту), ABANDON (пересчёт $\mathcal D(T)$ с текущими знаниями).

### X.1 Триггер рефлексии

$$\text{trigger\_reflection} = \left(\exists a_i: \text{status}(a_i)=\text{failed}\right) \ \lor\ \left(Q_{actual} < q_{min} - \delta_Q\right) \ \lor\ \left(\Delta_{plan} > \Delta_{plan,max}\ \land\ \text{status}\ne\text{success}\right)$$

— три независимых повода: явный отказ шага, сданный результат ниже порога качества с запасом $\delta_Q$ (не строго ниже — избегает дребезга на границе), или необычный по длине план (этап 6), не завершившийся успехом.

### X.2 Формула выбора реакции

$$\text{action} = \begin{cases}
\textbf{RETRY}, & k < k_{max}(a_i) \ \land\ \exists\ \text{альтернативный } a_i' \text{ с } u(a_i') \ge u(a_i)\cdot(1-\tau) \\
\textbf{ESCALATE}, & \Psi_{updated} > \psi_{max}\ \lor\ k \ge k_{max}(a_i) \\
\textbf{ABANDON}, & U_{recomputed}(T) \le 0
\end{cases}$$

где $\Psi_{updated}$ — риск, пересчитанный с учётом факта неудачи (наблюдаемый провал — это новая информация, повышающая оценку $P_{fail}$ для оставшейся части плана; конкретная формула обновления — экспоненциальное сглаживание, аналогичное §IV.2 ядра, применённое к $P_{fail}$), $U_{recomputed}(T)$ — полезность, пересчитанная с текущим (уже частично потраченным) $C_{spent}$ и обновлённым $\Psi_{updated}$.

**Обоснование структуры.** Три ветки соответствуют ровно трём реакциям, названным как открытая, нерешённая задача в самом начале этой сессии работы над документацией («обработка неверных ходов»/«цикл рефлексии») — теперь у каждой есть точное условие срабатывания, а не общая формулировка. ESCALATE — прямая связь с человеком: порог $\psi_{max}$ здесь — тот же гейт, что и на этапе 5, что обеспечивает согласованность (действие, ставшее слишком рискованным по ходу исполнения, эскалируется по тому же критерию, что заблокировало бы его на входе).

**[пример]** Один шаг плана (генерация черновика) дал результат ниже качества с первой попытки → есть альтернативный подход (другая модель, $u(a')\ge u(a)\cdot 0.9$) → **RETRY** с заменённым исполнителем (новый вызов UCB1, этап 7, но с обновлённой статистикой $\bar V_e$, учитывающей только что зафиксированную неудачу).

**Границы:** $\tau$ (допустимая просадка полезности альтернативы) — Часть XIII, запись R-3. Число RETRY-циклов ограничено сверху $k_{max}(a_i)$ той же формулой, что и в §VIII.2 — не отдельный, несогласованный лимит.

## Часть XI. Этап 11 — Обновление памяти и метрик

**Вход:** финальный статус задачи (success/abandoned), $Q_{actual}$, $\Phi_{task}$ (фактический, не прогнозный — считается по формуле §IV.2 ядра на реальных $P, C, T$).
**Выход:** обновлённые $\Phi_{historical}, \Upsilon_k, H$ — по формулам ядра (§IV.2, §IV.5, §IV.7), без изменений здесь; этот этап фиксирует **порядок** и **полноту** записи, отсутствовавшие в исходных документах.

### XI.1 Порядок обновления (важен, не может выполняться в произвольной последовательности)

$$\Upsilon_k(t{+}1) \leftarrow \text{update\_upsilon}(\ldots) \quad\to\quad \Phi_{historical}(t{+}1)\leftarrow\text{update via Kalman (§IV.2)} \quad\to\quad H(t{+}1) \leftarrow \text{compute\_h}(\ldots)$$

**Обоснование порядка.** $H$ (§IV.7 ядра) вычисляется из `rating_ratio`, который зависит от актуального $\Upsilon$, и из `balance_ratio`, зависящего от актуального баланса (производного от $\Phi_{historical}$) — если $H$ пересчитывается раньше, чем обновлены $\Upsilon$ и $\Phi_{historical}$, оно будет основано на устаревших данных на один шаг. Ни в одном исходном документе порядок операций не был зафиксирован явно — это чистый пробел реализации, который без явной фиксации здесь Jules (или любой другой исполнитель кода) мог бы реализовать в любом порядке, включая ошибочный.

### XI.2 Запись в память

Каждая завершённая задача порождает эпизодическую запись (`05_MEMORY_AND_STATE.md`) с полями как минимум: $(T_{raw}, \mathbf x, \mathbf p, \text{план } A, \text{история попыток}, Q_{actual}, \Phi_{task}, \text{триггеры рефлексии если были})$ — этого достаточно, чтобы этап III.1 (прогноз по похожим задачам) мог использовать эту запись в будущем, и чтобы `07_CALIBRATION_AND_VALIDATION.md` мог использовать накопленный лог для калибровки параметров §I.1.

Методология RLI — прямой, проверенный шаблон для того, как Space1 должен собирать собственные данные калибровки. Динамика показателя (проверено прямым поиском на момент написания, июль 2026): 2.5% на момент публикации → 4.17% (Opus 4.6+Claude Cowork, май 2026) → 6.3% (GPT-5.5) → 8.3% (Opus 4.8) → **16.1%** (Fable 5, июль 2026, актуальное значение — в исходных RLI-документах фигурировала чуть более ранняя цифра 15.8%). Рост в 6.4 раза за 9 месяцев — сигнал, что этот показатель двигают в первую очередь методы оркестрации (worker-critic, декомпозиция, QA), а не только базовая модель: сам факт, что Fable 5 обгоняет Opus 4.8 вдвое при сопоставимом релизе, при том что более новая Gemini 3 Pro на полном лидерборде RLI показывает всего 1.25% — подтверждает центральный тезис всех пяти разобранных документов о важности архитектуры поверх модели. **Отдельное предостережение, важное для собственной калибровки Space1:** авторы RLI, тестируя автоматического LLM-судью взамен ручной оценки, обнаружили систематическое завышение оценки новых моделей в 2.5–3 раза относительно людей-оценщиков — прямое предупреждение против использования одной и той же (или той же генерации) модели одновременно как исполнителя и как самопроверяющего критика без независимой калибровочной сверки.
