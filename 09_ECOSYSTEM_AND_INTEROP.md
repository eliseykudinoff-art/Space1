## Часть I. Реестр исполнителей — что стоит за `Candidates(a_i)`

`03_PIPELINE_MATH.md` §VII.1 определяет UCB1-выбор исполнителя для атомарного действия, но оставляет открытым, что именно образует множество `Candidates(a_i)` и как туда что-то попадает. Этот документ закрывает интерфейсный пробел.

### I.1 Четыре типа исполнителей

| Тип | Пример | Оплата | Реестр |
|---|---|---|---|
| Внутренний LLM-провайдер | `ai_super_router`, конкретная модель | Токены (уже в $C_{tokens}$, ядро §III) | `ModelRegistry` |
| MCP-инструмент | Файловый доступ, поиск, специализированный API | Обычно бесплатно/фиксировано | `ToolRegistry` |
| Внешний суб-агент (функциональный, разовый) | `04_ARCHITECTURE.md` §V — манифест на одно атомарное действие | Не оплачивается отдельно (часть текущей задачи) | `SubagentManifestRegistry` |
| Внешний субподрядчик (платное делегирование) | Другой ИИ-агент или фрилансер, берущий часть проекта за долю выплаты | Доля от $V$ (Часть VII) | `SubcontractorRegistry` |

Все четыре — частные случаи одной абстракции `ExecutorProfile` (уже введена как тип данных в `04_ARCHITECTURE.md` §IX), различающиеся полем `executor_type` и, соответственно, тем, какая функция оценки (Часть II) к ним применяется.

### I.2 Структура `ExecutorProfile` — расширение типа из `04_ARCHITECTURE.md`

```
ExecutorProfile:
  id, executor_type, capabilities: CapabilityVector
  cost_model, reliability_history, avg_latency
  trust: float  # Trust(e), ядро §IV.13
  compatibility: [protocol_ids]  # MCP / A2A / внутренний вызов
```

## Часть II. Оценка исполнителей

### II.1 Trust — практическая механика (формула уже в ядре §IV.13)

$$\text{Trust}(e) = w_{rep}\cdot\text{Reputation}(e) + w_{con}\cdot\text{ConstraintSatisfaction}(e)$$

Здесь фиксируется, откуда берутся оба слагаемых на практике: $\text{Reputation}(e)$ — та же структурная формула, что $\Upsilon$ (ядро §IV.5), применённая к истории взаимодействий *с этой сущностью*, обновляется по тому же Kalman-подобному правилу (ядро §IV.2/§IV.5), что и внутренние метрики — не отдельный, третий способ сглаживания истории. $\text{ConstraintSatisfaction}(e)$ вычисляется при регистрации и переоценивается на каждом использовании: доля деклараций из Agent Card/MCP-манифеста (заявленные возможности, лимиты, форматы), подтвердившихся на практике.

### II.2 ToolScore — многомерная оценка инструмента

$$\text{ToolScore}(tool) = w_1\cdot\text{Quality}+w_2\cdot\text{Speed}+w_3\cdot\text{Reliability}+w_4\cdot\text{Compatibility}+w_5\cdot\text{Cost}+w_6\cdot\text{Coverage}$$

Пересчитывается после каждого использования (не разово при регистрации) — источник: присланный ранее документ «Интеграция лучших мировых разработок» §9, формула принята без изменений по существу. **Связь с UCB1 (`03` §VII.1):** $\text{ToolScore}$ не заменяет $\bar V_e$ формулы UCB1 — является одним из входов при первичном ранжировании кандидатов до применения UCB1 (дешёвый предварительный фильтр, тот же принцип, что $EV(j)$ в `06_EXTERNAL_ENVIRONMENT.md` §I.1 для рыночных возможностей).

### II.3 Ξ — Executor Function (перенесена из архива ядра)

$$\Xi(tool, \text{action}) = \alpha\cdot Q_{result} - \beta\cdot(O_{time}+O_{cost})$$

Была архивирована в `02_MATHEMATICAL_CORE.md` (Часть VI, запись «$\Xi_{task}$») как относящаяся к уровню исполнителя, не оркестратора — здесь получает окончательное место. Используется как $\bar V_e$ в UCB1 (`03` §VII.1): среднее по $\Xi$ за все прошлые вызовы этого исполнителя на действиях данного типа.

**Границы:** $\Xi \in (-\infty,\infty)$, коэффициенты $\alpha,\beta$ — Часть IX (требуют калибровки, тот же статус, что был в архиве ядра).

## Часть III. Tool Acquisition Pipeline

**Источник:** присланный документ «Интеграция лучших мировых разработок» §6 (пайплайн из GitAgent-практики), формализован здесь.

$$\text{поиск} \to \text{оценка} \to \text{sandbox} \to \text{тестирование} \to \text{метрики} \to \text{ранжирование} \to \text{регистрация}$$

**Отличие от исходного описания источника** (там пайплайн был декларативным списком шагов без экономики) — каждый шаг здесь явно завязан на уже существующие функции ядра, не изобретает новую логику:

1. **Поиск** — по явному запросу (отсутствующая способность обнаружена на этапе декомпозиции, `03` §VI: $\mathbf x_{a_i} \not\preceq \mathbf x$) или проактивно (Skill Demand Forecasting, `06` §I.3, Пост-MVP).
2. **Оценка** — экономическая, до какой-либо установки: $\Xi_{predicted}$ по декларации возможностей (Agent Card/README), не по факту использования (оценка отсутствующих данных — тот же принцип холодного старта, что `03` §III.1, приоры вместо истории).
3. **Sandbox** — обязательный технический гейт, не решение оркестратора: новый инструмент получает `trust=0` и `Candidates(a_i)` вход только для некритичных, обратимых действий (низкий $\Psi$) до накопления реальной истории.
4. **Тестирование** — набор синтетических вызовов с известным ожидаемым результатом (аналог валидации навыка, `05` §V.2, тот же гейт `success_rate > 0.7` для перехода из sandbox в общий реестр).
5. **Метрики** — первичные значения $\text{ToolScore}$ (§II.2), $\Xi$ (§II.3) на синтетических вызовах.
6. **Ранжирование** — относительно уже существующих исполнителей той же способности (не абсолютное — новый инструмент оценивается против того, что уже решает эту задачу, не в вакууме).
7. **Регистрация** — попадание в `ToolRegistry`/`SubagentManifestRegistry` (§I.2), доступность для UCB1 (`03` §VII.1) с этого момента.

**Экономическая оценка (дополнение к декларативному списку источника):** каждый шаг имеет $C_{acquisition}$ (стоимость времени/токенов на поиск+тест) — сама Tool Acquisition проходит через тот же гейт $\mathcal D(T)$-подобной логики: приобретать новый инструмент имеет смысл, если $VoI(\text{новый инструмент}) > C_{acquisition}$ (та же формула VoI, ядро §IV.9, применённая не к уточняющему вопросу, а к решению «стоит ли исследовать этот инструмент»).

## Часть IV. Typed DSL для композиции инструментов

**Источник:** `FREELANCE-OPT_v3.0_Complete_Architecture.txt` §4.1 — конкретные, типизированные контракты для примитивов, используемые декомпозицией (`03_PIPELINE_MATH.md` §VI, Program Synthesizer) для формальной проверки плана **до** исполнения, не только после.

$$\{\text{pre}\}\ \text{action}\ \{\text{post}\}$$

**Пример примитивов** (перенесены как иллюстрация конкретной формы контракта, не как исчерпывающий список — реальный набор примитивов растёт вместе с `ToolRegistry`):

```
READ_FILE(path):
  pre: exists(path) ∧ has_permission(path, READ)
  post: returns(content) ∧ content_type_matches(path.extension)

WRITE_FILE(path, content):
  pre: has_permission(path, WRITE) ∧ (¬exists(path) ∨ has_permission(path, OVERWRITE))
  post: exists(path) ∧ read(path) = content

RUN_COMMAND(cmd, timeout):
  pre: is_whitelisted(cmd) ∧ sandbox_available()
  post: returns(exit_code, stdout, stderr) ∧ exit_code ∈ ℤ
```

**Использование в декомпозиции.** Прежде чем план $A=(a_1,\ldots,a_n)$ передаётся на исполнение (`03` §VII), проверяется **type checking** между выходом $a_i$ и входом $a_{i+1}$ (post-условие одного шага удовлетворяет pre-условию следующего) — формальная, дешёвая проверка **до** траты ресурсов на исполнение, отличная от Verifier (`03` §VIII.6), который проверяет уже полученный результат. Обнаруженное несоответствие на этом этапе возвращает план на пересборку (`03` §VI), не доходя до Этапа VII.

**Связь с sandbox (§III, шаг 3).** Новый, ещё не проверенный инструмент по умолчанию не имеет объявленного контракта $\{\text{pre}\}\ldots\{\text{post}\}$ — до появления контракта (составляется по итогам тестирования, §III шаг 4) инструмент недоступен для использования в формально проверяемых цепочках, только в изолированных, некритичных вызовах.

**Границы:** type checking — необходимое, не достаточное условие корректности плана (проходит формальную проверку типов, не гарантирует содержательный успех — это по-прежнему роль Verifier).

## Часть V. Протоколы связи с внешним миром

Решения приняты ранее (`Space1_Documentation_Rewrite_Plan.md`, реестр решений) — здесь фиксируется практическое применение, не переоткрывается.

### V.1 MCP — инструменты

Уже частично реализовано в коде (`digital_garden/protocols/mcp_client.py`) — используется как основа Tool Manager (`04_ARCHITECTURE.md` §IV.5), не переписывается заново. `ToolRegistry` (§I.2) хранит MCP-манифест каждого зарегистрированного сервера; `ConstraintSatisfaction` (§II.1) сверяется именно с декларациями этого манифеста.

### V.2 A2A — связь с внешними агентами

Принято как основа связи с внешними агентами (production-ready с января 2026, единый фонд Linux Foundation вместе с MCP — проверено веб-поиском в предыдущей сессии). `Agent Card` внешнего агента — источник для заполнения `ExecutorProfile.capabilities` и первичного значения `ConstraintSatisfaction`. Обнаружение внешних агентов через A2A происходит тем же путём, что Tool Acquisition (§III), с той разницей, что «тестирование» (шаг 4) для агента — не синтетические вызовы конкретной функции, а пробная передача одного низкорискового атомарного действия целиком.

### V.3 AP2 — платежи

Принято как основа для платного делегирования (Часть VII — Subcontractor Network) и для приёма оплаты от клиентов, где применимо. Не переопределяется здесь математически — `margin` (Часть VII.2) и вся денежная сторона уже выражены в терминах ядра ($\Phi$, $C$).

### V.4 Отклонённый протокол доверия

ERC-8004 (ончейн-реестр доверия) — рассмотрен и осознанно отклонён (зафиксировано ранее как решённый пункт реестра решений): избыточная инфраструктурная сложность для MVP при том, что `Trust(e)` (§II.1) уже даёт работающий, более простой механизм. Сохранён в Часть X как опция при выходе на действительно недоверенную, полностью децентрализованную сеть агентов — не актуально, пока Space1 работает через известные платформы и протоколы (MCP/A2A) с собственной, не блокчейн-репутацией.

## Часть VI. Обнаружение и реестр суб-агентов

### VI.1 От манифеста (`04_ARCHITECTURE.md` §V) к реестру

Манифест суб-агента (декларативный YAML, одноуровневая иерархия) — формат одной записи. Здесь — как записи попадают в `SubagentManifestRegistry` и обнаруживаются на этапе VII пайплайна: явная регистрация (манифест создан и подтверждён владельцем системы, для внутренних функциональных суб-агентов) либо через A2A-обнаружение (§V.2, для внешних).

### VI.2 Предпочтение CLI/API-инструментов над GUI-автоматизацией

**Из разбора RLI-документов (сессия 2026-07-16):** CLI-scaffold показывает более высокий automation rate, чем Computer-Use-Agent (GUI) для текущих моделей — не абсолютное правило, но правило по умолчанию при выборе между двумя равноценными по возможностям инструментами. Отражается в ToolScore (§II.2): компонента $\text{Compatibility}$ для GUI-инструментов получает понижающий множитель относительно эквивалентного по функциональности CLI/API-инструмента, если оба доступны для одного и того же действия. Не абсолютный запрет на GUI-автоматизацию — для задач, где API не существует (легаси-системы, часть веб-интерфейсов), GUI остаётся единственным путём.

## Часть VII. Subcontractor Network (Пост-MVP)

**Источник:** «Оптимизатор фриланс-агента» (сессия 2026-07-17) — агент как генеральный подрядчик, делегирующий часть проекта внешним субподрядчикам за маржу. Формально относится к типу исполнителя «внешний субподрядчик» (§I.1), но требует дополнительного аппарата, не нужного для трёх остальных типов.

### VII.1 Выбор субподрядчика

$$S_i = \frac{\text{JSS}_i\cdot\text{SkillMatch}_i}{\text{Rate}_i\cdot(1+\text{Risk}_i)}$$

— структурно аналогична $EV(j)$ (`06_EXTERNAL_ENVIRONMENT.md` §I.1), но с ролями заказчика и исполнителя, поменянными местами (Space1 здесь выбирает, кому доверить работу, а не кого убедить нанять себя).

### VII.2 Экономика делегирования

$$M = V_{client} - \sum_i c_i\cdot V_i - C_{overhead}, \qquad B_i = \min(0.2\cdot V_i,\ B_{max})$$

$M$ — маржа агента, $B_i$ — репутационный залог субподрядчика (защита от недобросовестного исполнения), $C_{overhead}$ — стоимость координации (уже частично покрыта $mkt\_C\_comm$-подобной величиной из более ранней сессии по `UNIFIED_MATHEMATICAL_FRAMEWORK_v4.0.md`).

### VII.3 Атрибуция вклада — значение Шепли

$$\varphi_i = \sum_{S\subseteq M\setminus\{i\}} \frac{|S|!(|M|-|S|-1)!}{|M|!}[R(S\cup\{i\})-R(S)]$$

— та же формула, что уже назначена методом калибровки факторов $\beta_i,\gamma_{ij}$ (ядро §IV.2, Часть V, запись Φ-1), применённая здесь к другой задаче: справедливое распределение выручки/репутационного эффекта между несколькими субподрядчиками одного проекта. Переиспользование метода, не второе, отдельное изобретение.

**Статус:** Пост-MVP целиком — требует уже работающего реестра исполнителей с историей (§I–II), которого не будет в первых итерациях. Условие активации — Часть X.
