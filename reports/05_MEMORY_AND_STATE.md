## Часть I. Четыре типа памяти — рамка CoALA

Решение принято дважды, независимо, из двух разных источников (`Space1_Documentation_Rewrite_Plan.md`, реестр решений): академическая рамка CoALA (Sumers et al.) и, отдельно, разбор документов по Remote Labor Index — оба сходятся на одной и той же таксономии без пересечения источников, что само по себе усиливает уверенность в выборе больше, чем любой один источник по отдельности.

| Тип памяти | Что хранит | Пример для Space1 | Физический бэкенд |
|---|---|---|---|
| **Working** | Активное состояние текущего шага пайплайна | Текущий `StatusBlock` (`03` §II.2), текущий план $A$ | Контекстное окно LLM-вызова — не персистентно между задачами |
| **Episodic** | Конкретные прошлые события с привязкой ко времени | «Задачу такого-то типа для такого-то клиента делал 12 дней назад, вышло не с первого раза» | Векторная БД + временной индекс (Часть III) |
| **Semantic** | Факты и предпочтения, не привязанные к конкретному событию | «Этот клиент предпочитает лаконичный стиль», «в категории X дедлайны обычно недооценивают на 20%» | Key-value / графовое хранилище (Часть IV) |
| **Procedural** | Как делать — воспроизводимые процедуры | Skill Library: «как правильно рендерить 3D-визуализацию интерьера» | Skill Library с индексом для retrieval (Часть V) |

**Принципиальное разграничение, важное для реализации:** Memory Manager (`04_ARCHITECTURE.md` §IV.3) отвечает за *семантику* — что и зачем хранится в каждом из четырёх типов; Storage Manager (§IV.4 того же документа) — за физический бэкенд. Один тип памяти может использовать несколько физических хранилищ одновременно (например, Episodic — и векторную БД, и отдельный временной индекс, см. Часть III) — это не нарушение принципа, а обычное разделение по типу доступа.

## Часть III. Episodic Memory

### III.1 Формат записи

Уже определён как контракт данных в `03_PIPELINE_MATH.md` §XI.2 — не дублируется, только цитируется как обязательный к соблюдению здесь:

$$\text{Episode} = (T_{raw}, \mathbf x, \mathbf p, A, \text{история попыток}, Q_{actual}, \Phi_{task}, \text{триггеры рефлексии})$$

плюс поля, добавляемые на этом уровне: `timestamp`, `client_id` (если применимо), `embedding` (векторное представление для retrieval).

### III.2 Формула приоритета — извлечение и удержание в рабочем наборе

$$I(\text{episode}, t) = w_1 \cdot \text{Recency}(t) + w_2 \cdot \text{Importance} + w_3 \cdot \text{Relevance}(\text{query})$$

$$\text{Recency}(t) = e^{-\lambda(t - t_{episode})} \quad\text{(та же экспоненциальная форма, что }\Phi_{forget}\text{, ядро §IV.6 — не новый механизм, переиспользование)}$$

$$\text{Importance} \in [0,1] \quad\text{— вычисляется в момент записи: } |Q_{actual} - q_{min}|\ \text{(чем дальше от ожидаемого — в любую сторону — тем важнее запомнить)}$$

$$\text{Relevance}(\text{query}) = \text{cosine\_sim}(\text{embed}(\text{query}), \text{embedding})$$

**Обоснование выбора Importance именно так.** Не «чем выше качество, тем важнее» (тривиально запоминало бы только успехи) и не «чем ниже, тем важнее» (только провалы) — отклонение от ожидаемого в любую сторону несёт больше информации для будущих решений, чем соответствие ожиданиям. Формула приоритета в целом (веса $w_1,w_2,w_3$) уже была установлена как интерфейсный контракт в `03_PIPELINE_MATH.md` §XV.2 — здесь она получает единственное развёрнутое определение, устраняя дублирование.

### III.3 Критичное ограничение — почему чистый векторный поиск не подходит для Episodic Memory целиком

Разбор источников по RLI (`Space1_Documentation_Rewrite_Plan.md`, находки 2026-07-16) содержит прямое предупреждение: чистый векторный RAG на temporal/последовательных задачах даёт околослучайный результат (F1≈0.29 против исправно работающих альтернатив) — сходство эмбеддингов не отражает порядок и временные связи между событиями, а именно они часто важны («что было до, что после», «сколько раз подряд», «стало ли лучше со временем»). **Практическое следствие:** Episodic Memory обязана иметь **отдельный временной индекс** (сортировка/фильтрация по `timestamp`, `client_id`), не только векторный — запросы вида «как прошли последние 3 задачи с этим клиентом» решаются временным индексом напрямую, не через похожесть эмбеддингов.

**Честно зафиксированное расхождение с альтернативным источником.** «Оптимизатор фриланс-агента» (полностью дочитан) предлагает более радикальное решение той же проблемы: не векторный поиск + временной индекс, а **Episodic Memory как граф с causal-рёбрами** («использовал для» / «привело к» / «альтернатива была») — поиск не по cosine similarity, а по causal path. Приводимый пример показателен: запрос «как интегрировать OAuth» через vector DB находит просто похожие по теме эпизоды («OAuth tutorial», «JWT guide»), тогда как граф находит причинно-следственную цепочку целиком («OAuth → проблема CORS → решение через proxy → проект X → клиент Y доволен») — то есть не просто похожий прецедент, а объяснение, почему он сработал. Решение здесь: для MVP остаётся вектор + временной индекс (Часть III.3–III.4) — полноценный граф с causal-рёбрами требует инфраструктуры, которую этот документ сознательно отклоняет для MVP (Часть X, запись M-3, аналогичное решение по Semantic Memory). Условие пересмотра: если после запуска станет ясно, что агенту систематически не хватает именно объяснения «почему сработало», а не просто «что было похоже» — это тот самый триггер для перехода к causal-графу, а не общее «когда-нибудь можно улучшить».

### III.4 Гибридный поиск — векторный + ключевые слова

Для запросов, где релевантность лучше определяется точным совпадением терминов (имя клиента, название технологии), чем семантической близостью, — гибридное ранжирование:

$$\text{BM25}(D,Q) = \sum_{q_i \in Q} \text{IDF}(q_i)\cdot\frac{f(q_i,D)\cdot(k_1+1)}{f(q_i,D)+k_1\cdot(1-b+b\cdot|D|/\text{avgdl})}$$

$$\text{RRF}(d) = \sum_{m\in\{\text{vector},\text{BM25}\}} \frac{1}{k+r_m(d)}$$

— Reciprocal Rank Fusion объединяет ранг документа по векторному поиску и по BM25 в одну оценку, не требуя нормировки шкал (проблема прямого смешивания cosine-similarity и BM25-скора, у которых разные, несравнимые диапазоны значений). Обе формулы — общепринятые, устоявшиеся методы информационного поиска, не изобретены для Space1.

**Итоговый retrieval для Episodic Memory:**
$$\text{retrieve}(query, k) = \text{top-}k\ \text{по}\ I(\text{episode}) \cdot \text{RRF}(\text{episode})$$
— приоритет (Часть III.2) и релевантность запросу (RRF) перемножаются, не складываются: старый, неважный, но идеально релевантный по ключевым словам эпизод не должен вытеснять недавний важный эпизод с чуть менее точным совпадением.

**Границы:** $I \in [0,1]$ при условии $w_1+w_2+w_3=1$; `retrieve()` всегда возвращает не более $k$ эпизодов (параметр, Часть IX).

## Часть IV. Semantic Memory

**Определение:** факты и предпочтения, не привязанные к конкретному событию во времени — то, что осталось бы верным, даже если удалить историю о том, когда и как это было узнано.

**Формат:** key-value с возможностью графовых связей там, где это естественно (клиент → предпочтения → связанные проекты) — не полноценная графовая БД с нуля, а key-value хранилище с полем `related_to` для простых связей. Полноценный граф знаний — Часть X, отклонённая для MVP версия.

**Источник записи:** semantic-факты не создаются напрямую — извлекаются из Episodic Memory при консолидации (периодическая фоновая операция, не на каждом шаге пайплайна): если несколько эпизодов с одним клиентом стабильно показывают одну и ту же закономерность (например, «этот клиент трижды просил укоротить текст») — она поднимается в Semantic Memory как явный факт, а не остаётся implicit в сумме эпизодов, которую пришлось бы каждый раз заново «вычитывать» векторным поиском.

**Формула обновления уверенности** (уточнено по итогам полного дочитывания «Оптимизатора фриланс-агента» — заменяет прежнюю расплывчатую «долю подтверждающих эпизодов» явным, асимметричным правилом):

$$\text{confidence}_{t+1} = \begin{cases}
0.9\cdot\text{confidence}_t + 0.1, & \text{новый эпизод подтверждает факт} \\
0.7\cdot\text{confidence}_t,\quad \text{contradictions}\mathrel{+}=1, & \text{новый эпизод противоречит факту}
\end{cases}$$

$$\text{confidence}_{\text{effective}} = \text{confidence}_t \cdot (0.5)^{\text{contradictions}} \cdot e^{-\lambda\cdot\text{age}}$$

**Обоснование асимметрии.** Подтверждение усиливает факт медленно и с насыщением (множитель 0.9, асимптота к 1.0 — единичное совпадение не делает факт достоверным на 100%), опровержение ослабляет быстрее (множитель 0.7) и оставляет постоянный след (`contradictions` не обнуляется, штраф $(0.5)^{\text{contradictions}}$ действует на итоговую эффективную уверенность необратимо, в отличие от плавного затухания по времени $e^{-\lambda\cdot\text{age}}$, которое обратимо новым подтверждением). Это не симметричный байесовский счётчик, а сознательно смещённое в сторону осторожности правило: одно противоречие снижает доверие к факту сильнее, чем одно подтверждение его повышает — соответствует здравой эвристике «легче испортить репутацию факта, чем заслужить».

**Пример структуры записи:**
```
{
  "subject": "client_42",
  "predicate": "prefers_style",
  "object": "concise",
  "confidence": 0.8,
  "contradictions": 0,
  "derived_from": ["episode_17", "episode_23", "episode_31"],
  "last_confirmed": "2026-07-10"
}
```

**Границы:** `confidence_effective` пересчитывается при каждом обращении (не только при записи нового эпизода — временной множитель $e^{-\lambda\cdot\text{age}}$ меняется непрерывно); факт с `confidence_effective` ниже порога (Часть IX) не используется в `StatusBlock` (§II этого документа) — низкая уверенность не должна влиять на текущее решение агента как будто это установленный факт.

## Часть V. Procedural Memory — Skill Library

### V.1 Структура

```
Skill:
  name, domain, inputs, outputs, steps, examples
  success_rate, avg_cost, usage_count, last_used
```

### V.2 Извлечение навыка (после задачи)

$$\text{extract\_skill}(A, \text{attempt\_history}, \text{success}) \to \text{Skill} \mid \text{None}$$

Процедура: анализ трассы исполнения (последовательности $a_1,\ldots,a_n$ и их результатов) → идентификация переиспользуемого паттерна → абстрагирование конкретных параметров задачи в общую спецификацию (вход→выход) → валидация на отложенных примерах, если такие есть.

**Гейт на добавление в библиотеку:** навык добавляется, только если оцененный $\text{success\_rate} > 0.7$ на валидационных примерах — не после однократного успеха. Это защита от того, что после первого случайного успеха в библиотеку попадёт непроверенный, возможно, специфичный только для этой одной задачи «навык».

### V.3 Извлечение навыка (перед задачей) — ранжирование

$$\text{retrieve\_skill}(T, k) = \text{top-}k \text{ по } \text{similarity}(T, \text{skill})\cdot\text{success\_rate}(\text{skill})\cdot\text{recency}(\text{skill})$$

**Обоснование мультипликативной, а не аддитивной формы** (в отличие от Episodic Memory, где приоритет и релевантность объединены произведением двух факторов, а не трёх взвешенных слагаемых): здесь все три фактора — необходимые условия, не взаимозаменяемые веса. Навык, идеально релевантный по формулировке задачи, но с историческим `success_rate=0`, не должен быть извлечён ни при каких обстоятельствах — аддитивная формула допустила бы это при достаточно высокой релевантности, мультипликативная — нет (нулевой множитель обнуляет всё произведение).

### V.3a Tactics — поведенческий подтип навыка (по итогам полного дочитывания «Оптимизатора фриланс-агента»)

Отдельная категория Procedural Memory — не «как выполнить техническое действие», а «как повести себя в ситуации» (переговоры о цене, эскалация риска дедлайна, восстановление после ошибки, выбор темпа работы). Формально — тот же тип сущности (Skill), но со специфичной, более узкой структурой полей:

```
Tactic:
  name, trigger: (situation) -> bool, action: (situation) -> response
  success_rate, applicable_context
```

**Отличие от общего Skill (§V.1):** `trigger` — явное, проверяемое условие активации (не similarity-поиск по описанию задачи, а предикат над текущей ситуацией — например, «клиент назвал бюджет ниже минимально жизнеспособной цены»), `action` — не последовательность атомарных действий пайплайна, а шаблон коммуникативного ответа. Извлечение при необходимости (§V.3) для тактик заменяется прямым перебором активных `trigger`, отсортированных по $\text{success\_rate}\times\text{relevance}(\text{tactic}, \text{ситуация})$ — та же логика ранжирования, что и для навыков, но `trigger` может отфильтровать кандидата до ранжирования, а не только после.

**Разрешение конфликта нескольких сработавших тактик:** приоритет **безопасность > качество > скорость** — если тактика, ориентированная на скорость (например, «быстрая победа для тревожного клиента»), противоречит тактике, ориентированной на осторожность при высокой технической сложности задачи, побеждает вторая; разрешение конфликта не требует нового механизма — использует уже существующий $H$ и $\Psi$ (ядро §IV.4, §IV.7) как арбитр: при повышенном $\Psi$ или пониженном $H$ тактики категории Recovery/осторожность получают приоритет над тактиками категории Speed независимо от их индивидуального `success_rate`.

**Примеры конкретных тактик** (перенесены как готовые, не гипотетические — источник даёт по 2 примера на 4 категории): *Negotiation* — «Anchor High» (ставка = оценка×1.3 при неизвестном бюджете клиента), «Walk Away» (вежливый отказ с альтернативой при бюджете <70% от минимально жизнеспособной цены — не «hard no», сохраняет отношения); *Escalation* — «Early Warning» (уведомление о риске срыва дедлайна заранее, а не в последний момент), «Partial Delivery» (сдача частичного результата с явным планом на остальное); *Recovery* — «Own It Fast» (признание ошибки в течение часа с указанием причины и превентивной меры), «Overdeliver After Fail» (бесплатный бонус к объёму после сбоя, до того как клиент попросит); *Speed* — «Quick Win First» (быстрый черновой результат для тревожного нового клиента), «Slow Down For Complex» (явное замедление и обоснование при высокой технической сложности, даже если клиент торопит).

**Статус:** MVP использует небольшой стартовый набор тактик (перечисленные выше 8 — разумная начальная библиотека, не требует обучения с нуля); механизм извлечения/затухания (§V.3–V.4) применяется к ним без изменений.

### V.4 Затухание неиспользуемых навыков

$$\text{status}(\text{skill}) = \begin{cases}
\text{active}, & \text{days\_since\_use} < 30 \\
\text{stale}, & 30 \le \text{days\_since\_use} < 90 \\
\text{archived}, & \text{days\_since\_use} \ge 90
\end{cases}$$

Пересчитывается фоновым процессом (не на каждом шаге пайплайна — периодическая задача, аналогично такту пересмотра Mission, ядро §IV.12). `stale`-навыки участвуют в retrieve с понижающим множителем к `recency`; `archived` — не участвуют вовсе, но не удаляются физически (доступны для ручного восстановления и для анализа при калибровке, `07_CALIBRATION_AND_VALIDATION.md`). Источник механизма — практика Hermes Agent Curator (проверено веб-поиском ранее, `Space1_Documentation_Rewrite_Plan.md`), решает конкретную проблему, которую первоначальная схема (навык создаётся и живёт вечно) не решала — постепенное замусоривание библиотеки навыками, утратившими актуальность (изменившиеся API, устаревшие подходы).

**Границы:** `success_rate` навыка обновляется по той же экспоненциально-сглаживающей схеме, что $\Phi_{historical}$ и $\Upsilon$ (ядро §IV.2, §IV.5) — не отдельный, третий способ сглаживания истории.

**Параметры:** пороги 30/90 дней, гейт 0.7 — Часть IX.

## Часть VI. Хранилище — физический слой

Storage Manager (`04_ARCHITECTURE.md` §IV.4) не описывается здесь математически (сознательно, как и в архитектурном документе) — фиксируется только распределение ответственности между физическими бэкендами:

| Тип памяти | Бэкенд | Обоснование |
|---|---|---|
| Working | Контекстное окно (не персистентно) | Не требует хранилища как такового |
| Episodic | Векторный индекс + временной индекс (раздельно, Часть III.3) | Ни один индекс сам по себе не покрывает оба типа запросов (семантический / временной) |
| Semantic | Key-value с полем связей | Простая структура, не требует полноценного графа для MVP |
| Procedural | Skill Library с собственным векторным индексом (для similarity в §V.3) | Отдельный индекс — навыки ищутся не так, как эпизоды (по описанию задачи, не по содержанию) |

**Существующий код.** `digital_garden/core/memory.py` (плоское файловое хранилище с keyword-поиском) не покрывает ни один из четырёх типов в описанном виде — это черновая заготовка Storage Manager, требующая замены на всех уровнях, а не точечного расширения. Фиксируется здесь как известный технический долг, не устраняется в рамках этой волны документации (код не трогаем по вашему условию).

## Часть VII. Состояние агента

### VII.1 Режимы — два независимых измерения, не один автомат

Решение принято ранее (`Space1_Documentation_Rewrite_Plan.md`, реестр решений): вместо двух конкурирующих наборов режимов, найденных в исходном корпусе (Critical/Normal/Growth/Proactive из одного источника, Dormant/Active/Recovering/Suspended из `SYSTEM_MONITORING.md`), — два независимых измерения одного и того же состояния, а не выбор одного набора:

$$\text{OperationalStatus} \in \{\text{DORMANT}, \text{ACTIVE}, \text{RECOVERING}, \text{SUSPENDED}\}$$
$$\text{StrategicPosture} = \text{derive}(H, \text{Mission}) \in \{\text{CRITICAL}, \text{NORMAL}, \text{GROWTH}, \text{PROACTIVE}\}$$

**OperationalStatus** — техническое состояние процесса (есть ли активная задача, идёт ли восстановление после сбоя, приостановлен ли агент вручную) — управляется событиями пайплайна напрямую (новая задача → ACTIVE, серия ESCALATE из рефлексии `03` §X → RECOVERING, ручная остановка → SUSPENDED, простой → DORMANT).

**StrategicPosture** — не отдельный автомат с собственными переходами, а **чистая функция** от уже вычисленных величин: $H$ (ядро §IV.7) и текущего типа Mission (ядро §IV.12). Например: $H<0.5$ → CRITICAL независимо от Mission; $H\ge 0.5$ и Mission=SURVIVAL/MAINTENANCE → NORMAL; $H\ge 1.0$ и Mission=GROWTH/MAXIMIZE → GROWTH; проактивные импульсы (`01_CONCEPT.md` §II.2) разрешены только при PROACTIVE. Точное отображение — Часть IX (не новые калибруемые параметры, а прямое использование уже существующих порогов $H$ из ядра §IV.7).

**Почему это не два конкурирующих решения, а согласованное.** `OperationalStatus` отвечает на вопрос «что физически происходит», `StrategicPosture` — «в каком режиме принимаются решения». Задача может быть в работе (`ACTIVE`) при этом в стратегически осторожном режиме (`CRITICAL`, если $H$ низкий) — это два разных, ортогональных факта об одном моменте времени, не взаимоисключающие состояния одного автомата.

### VII.2 Версионирование изменяемых объектов состояния

По итогам разбора присланного ранее документа «Интеграция лучших мировых разработок» (§4, идея версионирования по образцу GitAgent) — каждый из объектов, которые самообучение (ядро §VIII.4, EWC) имеет право изменять, обязан вести историю изменений, не только текущее значение:

$$\text{VersionedObject} = (\text{current\_value}, \text{history}: [(\text{value}, \text{timestamp}, \text{reason})])$$

применяется к: весам Mission (`PolicyParams`, ядро §IV.12), калибруемым параметрам ядра (Часть V `02_MATHEMATICAL_CORE.md`), Skill Library (уже подразумевает историю через `usage_count`/`last_used`, здесь формализуется единообразно с остальными). **Не применяется** к Episodic Memory (она сама по себе уже является историей, обёртка избыточна) и к hard-правилам Γ (они не подлежат автономному изменению вовсе, `01_CONCEPT.md` §III.3 — версионировать нечего).

**Обоснование, почему это в документе про память, а не отдельно.** История изменений параметров — это, по сути, ещё один вид эпизодической памяти (события во времени), просто не о задачах, а о самом агенте как объекте — переиспользует ту же логику хранения (Часть III), не создаёт пятый тип памяти.

**Границы:** `history` не хранится бесконечно — подлежит тому же затуханию, что Episodic Memory (Часть III.2, `Recency`) при превышении объёма (Часть IX).
